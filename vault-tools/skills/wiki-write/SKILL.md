# wiki-write

产出或修订一篇 wiki 沉淀页，按顺序调用宿主通用子智能体执行四个技能——`wiki-write-explore`、`wiki-write-draft`、`wiki-write-humanize`、`wiki-write-review`，靠文件交接，验收留在这一层自己跑，不交给任何子 agent。

## 怎么派发每一步

下文的 `wiki-write-explore`、`wiki-write-draft`、`wiki-write-humanize`、`wiki-write-review` 都是技能名。每步新起一个宿主通用子智能体，不调用插件专用工具或预设。

派发前，从本文件的位置解析 `../<技能名>/SKILL.md` 与 `../wiki/SKILL.md` 的绝对路径。prompt 点名这两份文件，要求先读取；同时写明库根、目标页、落点区门面、`<slug>`、输入文件、允许写的文件与本步约束。把库根作为子智能体工作目录。不能假定它继承了主会话的技能或前一步的上下文。

| 步骤技能 | 执行约束 |
|---|---|
| `wiki-write-explore` | 只产出素材与调研笔记，不写正文；禁止联网的场景要在 prompt 中明确 |
| `wiki-write-draft` | 只用交接材料，不联网；shell 只运行 `./.wiki/bin/wiki` 的建页与检查命令 |
| `wiki-write-humanize` | 只读改指定正文范围，不新增内容、不联网、不运行 shell |
| `wiki-write-review` | 只读改指定正文范围及对应账本，不联网、不运行 shell；最终验收由主会话执行 |

这些是技能执行约束，实际工具权限由宿主通用子智能体的配置决定。宿主提供合适的受限模式时使用它；技能本身不创建工具隔离。当前会话没有通用子智能体能力时，说明缺少该能力并停止派发，不声称已经完成这些步骤。

## 两根轴

先判新建还是修订，新建再判场景。

### 轴一 · 新建还是修订

| 入口 | 怎么判 | 走哪几步 |
|---|---|---|
| 新建整页 | 目标页不存在 | 按轴二定，末尾恒是 `wiki-write-humanize` → `wiki-write-review` |
| 改已有页 | 目标页已存在 | `wiki-write-humanize` → `wiki-write-review` |

判据只看一件事：目标路径这一个文件能不能 `Read` 到。标题在别处出现过、有没有草稿散落在 `.wiki/tmp/` 之类的地方，都不算数。改已有页这条路省掉 explore 和 write，因为调研已经在正文里了：humanize 直接对着现成的文字去味，review 直接摘现成的非知识句子。

错别字、链接失效这类微改不进这条流程，直接改，不必因为动了一个字就走两步或四步。

**修订还分两种，两步那条只管其中一种。** 正文里的调研够用、只是写得不好，走 `wiki-write-humanize` → `wiki-write-review` 两步。正文的**结构或取材本身要重来**——比如小节按错误的轴切、或者当初该采的材料没采——那要按轴二重走一遍前面几步，末尾再接那两步。判据：这次要改的东西，现有正文里有没有对应的事实支撑。没有就得重新取材，不是改写能解决的。

判错这一条的代价是白跑：拿着一份缺料的正文去味、摘待办，改完仍然缺料。

入口判完不等于流程完：全四步要四个 agent 都返回、正文通过下面的验收才算完；两步要 `wiki-write-humanize` 和 `wiki-write-review` 都返回、正文通过验收才算完。中途停在任何一步，这次 wiki-write 都不算完成。

判错的两个方向后果不对称。误判成「新建」，`wiki-write-draft` 会对着一页已经写好的正文重新落笔，拿一份更薄的材料覆盖已有内容，`Edit` 不会报错——**这个方向的损失最不容易被察觉**。误判成「已有」，`wiki-write-humanize` 会对着一个不存在的路径或空文件动作，找不到目标当场报错，流程卡在这一步，但至少能立刻发现。判不准的时候，先用一次 `Read` 确认目标路径在不在，不要凭标题或记忆判断——入口判据只认这一次检查的结果。

### 只处理未提交的改动

`wiki-write-humanize` 与 `wiki-write-review` 只对着**这次没提交的改动**动手：已提交的正文算上一轮收过，不再从头读一遍。这两步不运行 shell，范围由编排层在库根算好、写进 prompt：

```bash
git ls-files --error-unmatch -- "<目标页>" >/dev/null 2>&1 || echo 全页
git diff -U0 HEAD -- "<目标页>" | awk '/^@@/{split($3,a,",");s=substr(a[1],2);n=(a[2]==""?1:a[2]);if(n>0)print s"-"s+n-1}'
```

| 输出 | 怎么起 |
|---|---|
| `全页`（页还没进 git） | 范围是全页，整页处理 |
| 一组行号段（`12-18`、`40-40`…） | 行号段原样写进 prompt |
| 空（已进 git、没有改动，或只删了行） | 不起这两步，告诉人「这页没有未提交的新增或改写」；人明确要整页重收，才按 `全页` 起 |

review 的范围要在 humanize 返回后**重算一次**：humanize 改完行号会挪，拿旧行号起 review 会指错位置。

### 轴二 · 新建时判场景

判据是落点在哪个区，因为区已经把「材料从哪来、顺序能不能颠倒」分开了。

| 场景 | 落点 | 前面几步 | 规则读哪份 |
|---|---|---|---|
| 拆一个外部项目 | `学习/<System>/` | 钉基线 → `wiki-write-draft` 写猜测页标 draft → `wiki-write-explore` 取六路输入 → `wiki-write-draft` 逐条对账 | `学习/学习.md` |
| 练一个框架或库的用法 | `学习/<System>/` | 钉基线（demo 仓 commit + 被练系统版本）→ 在 demo 仓写脚本并实跑 → `wiki-write-draft` 按练习变体写章页，带上实跑输出 | `学习/学习.md`「练习变体」 |
| 拆一个内部系统 | `系统/<域>/` | 不钉基线（活仓随开发在动）→ `wiki-write-draft` 写猜测页标 draft → 取材（多「问人」与评审纪要）→ `wiki-write-draft` 逐条对账 | `系统/系统.md`、[anchors.md](anchors.md) |
| 写业务域的规划页 | `系统/<域>/` | `wiki-write-explore` 清点已归档的内部文档（**不联网**） → `wiki-write-draft` | `系统/系统.md` |
| 写行业矩阵的跨平台读法页 | `系统/<X>行业矩阵/` | `wiki-write-explore` 清点矩阵成员各平台已定版的域页（**不联网**）→ `wiki-write-draft`；单域内的对象与字段只引用域页、不在矩阵页重写 | `系统/系统.md` 的行业矩阵相关规则 |
| 沉淀一次会议、听录、分享 | `经历/观察/YYYY-MM/` | 素材已在 `raw/`，`wiki-write-explore` 只出调研笔记不联网 → `wiki-write-draft` 写成一篇观察文档（完整过程留在这里）；再往认知沉淀由人指定，指定后对目标页另走一次 wiki-write | `经历/经历.md` |
| 学一篇文章或一个主题 | `知识/` | `wiki-write-explore` 联网抓 → `wiki-write-draft` | `知识/知识.md` |
| 沉淀书的一章 | `知识/` | 原文已在 `raw/book/X/章节/<号> <标题>.md`，`wiki-write-explore` 只在要补外部材料时起 → `wiki-write-draft`（按概念切，一章可落多页、也可并进已有页） | `知识/知识.md`、`wiki` 技能 [sources.md](../wiki/sources.md)「读书」 |

每条路末尾都接 `wiki-write-humanize` → `wiki-write-review`，那两步与场景无关：不管写的是什么，中文都会长 AI 味、都会混进写作指令。

**起每一步时把落点区门面 `<区>/<区>.md` 的路径写进 prompt**，跟目标页路径、`<slug>`、该读哪个交接文件并列；方法页由门面的「读哪份」表指，子 agent 顺着读。子 agent 不会自己去找，规则不在它眼前就等于没有。

**prompt 里别带自己的猜测。** 编排层顺手写一句「看看是不是跟 X 是同一条约束」，子 agent 多半会顺着这条线去找印证，然后把你的猜测当结论写回来。真要提，就明标成「这是我的猜测，去核对，错了就说错了」。

**越界改动靠 `git status` 查，不靠子 agent 自报。** `wiki-write-draft` 同时有 `Write` 和 `Edit`，它能改的不只是目标页，而这条边界只能写在提示词里、没有工具层的约束。每一步返回之后跑一次 `git status`，确认动的只有该动的文件。实跑里出现过：agent 改了另一页，报告里说那是「另一个并行会话的在制品」——**它未必是在推卸，多个会话同时开着是常事，但你不能凭报告就信**，得自己看。

### 拆解那两条为什么先写后查

前两条的第二步是「写猜测页」而不是「先调研」，跟另外两条相反。这是那份方法定的：先查再写，手上只剩摘抄，第四步「逐条对账」就没有可证伪的东西。对账落三类判定，只有 divergence（它有我没猜到）与 absence（我写了代码里没有）带来新知识，而这两类要求先有一份写下来的猜测。

`wiki-write-draft` 按技能约束不联网，适合写猜测页这一步——它手上除了已有理解什么都没有。

### 编排层自己做的两件

钉基线与收尾不派给子 agent。钉基线要改 `.wiki/anchors.conf` 并确认克隆就位，收尾要 `wiki page mark <路径> stable`，两件都要 `Bash`。内部系统没有钉基线这一步（`系统/` 不进 `anchors.conf`），只剩收尾。

### 粒度是一页，不是一条链

建设推进的方法可能包含现状、痛点、价值、战略、规划、项目和故事等环节；按目标区门面指向的方法选择本轮范围，需要写的每一页**各走一次 wiki-write**。这个技能不编排整条链；环节的依赖、迭代方式与完成判据归相应方法管，不把七环当作所有任务的固定顺序。

## 顺序执行，不返工

**不并行。** 四个 agent 里任何两个凑在一起跑，改的都是同一份正文文件——同时起两个，谁先落盘、谁又把谁盖掉，事后连 diff 都理不清楚。每一步都要等上一步的 agent 返回、确认它该写的文件已经在磁盘上，再起下一步。

**不打回重跑。** `wiki-write-review` 挑出来的问题一律记账——欠人的动作与过程账都进 `.wiki/review/` 的账本——交给人处理，不重新起 `wiki-write-draft` 再写一遍。`wiki-write-draft` 落笔时已经把调研笔记和 `raw/` 素材揉进了具体的措辞与取舍，这份取舍本身就是中间产物；推倒重写等于让下一个 `wiki-write-draft` 凭一份更薄的材料重新猜一遍，写出来的不会是同一篇。

每一步起 agent 的 prompt 里，三样都要点名：目标页路径、`<slug>`、这一步该读哪个文件；humanize 与 review 再加第四样：改动范围（`全页` 或行号段，见上文「只处理未提交的改动」）。子 agent 不会自己回去翻上一步的产出落在哪，没点名就找不到。

## 交接

`<slug>` = 目标页文件名去掉扩展名（`C4 Model.md` → `C4 Model`）。工作区在 `.wiki/tmp/<slug>/`，已在 `.gitignore` 内。

| 步 | 读 | 写 |
|---|---|---|
| explore | 网 / 既有 `raw/` | `raw/` 素材 + `.wiki/tmp/<slug>/00-调研笔记.md` |
| write | 调研笔记 + 它点名的 `raw/` | 正文页 |
| humanize | 正文页 | 正文页（只改散文段） |
| review | 正文页 | 正文页（非知识句删掉）+ `.wiki/review/` 账本（待办清单、删句账、判过留的） |

四步的交接以这张表和磁盘文件为准，不依赖上下文继承。依次派通用子智能体执行四个技能：[wiki-write-explore](../wiki-write-explore/SKILL.md) → [wiki-write-draft](../wiki-write-draft/SKILL.md) → [wiki-write-humanize](../wiki-write-humanize/SKILL.md) → [wiki-write-review](../wiki-write-review/SKILL.md)。起下一步之前，先确认表里「写」那一列的文件已经在磁盘上，再把「读」那一列的路径写进下一步的 prompt；跳过任何一步（常见是写完直接验收），这次 wiki-write 不算完成。

**新建页的 `<slug>` 分两段。** 工作区路径要在起 explore 之前就定下来，而那时候还不知道这篇讲什么、该落哪个区、页叫什么名——先用一个临时 slug 开工，explore 回来、落点定了，再由编排层把工作区改名成正式 slug。别为了凑出一个 slug 而提前拍板落点。

**开跑前先看 `.wiki/tmp/<slug>/` 有没有旧残留。** 同一个 slug 跑第二次（上一次失败中止、或者这次是重写），上一轮的中间产物还在那儿，下一步会读到过期的东西。有就先清掉。

**文件在磁盘上不等于这一步成了。** 子 agent 可能返回成功、文件也确实写出来了，而内容是一份失败诊断或者半截东西。起下一步之前打开看一眼：调研笔记的三节里有没有实质内容、正文页有没有真的按骨架长出来。**内容不成立就停下来问人，不要硬着头皮起下一步**——喂一份空笔记给 `wiki-write-draft`，它只会把空笔记写成一页空话。

## 验收（编排层自己跑，不交给子 agent）

humanize 与 review 只负责各自的正文处理，不运行 shell，也不代替主会话验收。主会话亲自执行下面的命令并核对结果，不能把子智能体的成功报告当成验收通过。

```bash
./.wiki/bin/wiki check
```

页里出现反引号包住的外部代码标识符时，再加一条：

```bash
./.wiki/bin/wiki page anchor <目标页>
```

两条命令的判据是退出码。任一非零，整个流程判定失败：把失败输出原文照抄给人，不静默放行，也不自己回去悄悄改正文再重跑一遍验收——改没改对留给人判断，这一层不代人做主。

两条都成功也不代表万事大吉。`wiki-write-humanize` 那步自己汇报的加粗、破折号手数不可全信：实测中它自报「6 处 / 93 行 / 6.45」，实际是「7 处 / 92 行 / 7.60」，两个数都偏乐观。密度远离阈值时这点误差不碍事，贴近阈值（比如 8.3）时却会把超标当达标放过去。所以验收这一步除了跑上面两条命令，还要照模式表的判据自己抽查一次去味的结果，不能只看 humanize 报的数字。

## 收尾

流程走完，提醒人两件事：`.wiki/tmp/<slug>/` 这份工作区可以删了；`.wiki/review/` 账本的待办清单与删句账各新增了哪几条（报条数，内容留给人自己去看）。

沉淀书的一章时还有一件：在进度页「## 知识沉淀」该章条目下逐页用 `[[页名]]` 登记写出或改动的页，条目**保持「· 沉淀中」**——不跑 `wiki book deposit --done`（它只认人的身份），提醒人确认后自己标完成。沉淀的四步流程见 [sources.md](../wiki/sources.md)「读书」。

不替人提交。wiki-write 到验收通过为止，git add 与 git commit 留给人自己决定什么时候做、怎么写提交信息。
