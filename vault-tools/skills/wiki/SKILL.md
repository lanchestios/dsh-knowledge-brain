# 格物致知 wiki

本文件是常驻部分：分区、目录规则、落点、命令。细则按场景放在同目录，用到再读：

| 场景 | 读 |
|---|---|
| 库还是空的，第一次上手 | [onboarding.md](onboarding.md)：第一个闭环——抓一篇文章 / 放一本书 / 起一页，从空到不空 |
| 查库里的内容、给会话补库内上下文（只读） | [wiki-read](../wiki-read/SKILL.md) |
| 新建或修订一篇沉淀页（调研 → 落笔 → 去味 → 摘待办） | [wiki-write](../wiki-write/SKILL.md) |
| 只改一页的某处：正文措辞、配图公式、frontmatter / mark / verify、外部代码基线 | `wiki-write` 下的 [writing.md](../wiki-write/writing.md)、[diagrams.md](../wiki-write/diagrams.md)、[diagram-reference/](../wiki-write/diagram-reference)、[metadata.md](../wiki-write/metadata.md)、[anchors.md](../wiki-write/anchors.md) |
| 归档素材、记沉淀账、读书 | [sources.md](sources.md)：raw 状态推导、cover、读书四状态 |
| 一本书从源文件整理到可读（转文本、补图、梳理、质检；扫描版转写） | [wiki-write-book-ingest](../wiki-write-book-ingest/SKILL.md) |
| 给一层子页排序 | [ordering.md](ordering.md)：`.folder.json`、`wiki.json`、导览文 |
| 改工具代码 | 源头在 dsh-knowledge-brain 插件包 `vault-tools/`（`.wiki/bin` 软链的指向处，readlink 可得）；说明见包内 `vault-tools/README.md` |

这些规则跨区通用，只定义在本技能里，别处只引用。区专属的读写规则（区内怎么找、骨架、变体、例外、验收清单、方法页指路）写在五区门面 `<区>/<区>.md`：`经历/经历.md`、`认知/认知.md`、`学习/学习.md`、`知识/知识.md`、`系统/系统.md`。门面是读写规则的一部分：往哪个区写，动笔前先读那个区的门面；在哪个区查，先读门面的「怎么读」一节。

## 六区

`raw/` 是格物，其余五区是致知：`经历/` 是来料，`认知/` `学习/` `知识/` `系统/` 是沉淀：

| 目录 | 放什么 | 判据 |
|---|---|---|
| `raw/` | 摄入的素材 | 别人写的。原件，只进不改 |
| `经历/` | 观察与实践，按月记 | 我经历过什么 |
| `认知/` | 见解、方法论、原则 | 我怎么想 |
| `学习/` | 拆过、练过的具体系统 | 我拆过、练过什么 |
| `知识/` | 外部习得的领域知识 | 我知道什么 |
| `系统/` | 业务域与其中的系统、项目 | 我在做什么 |

**`学习/` 与 `知识/` 按「会不会随上游过期」分。** 学习页断言的是一个具体系统在某个版本上的样子：读源码拆，断言「它在这个 commit 上是这么造的」；调 API 写 demo 练，断言「它在这个版本上是这么用的」。两种都得在 `anchors.conf` 钉基线才能回验。知识页写书、方法、判据，不绑版本。要钉基线才敢写的进 `学习/`。按「项目还是领域」分不开：Pi 和 Palantir Ontology 都是具体的外部产品。

`学习/` 与 `知识/` 搭配着用：概念只写在 `知识/`，学习页用 `[[双链]]` 指过去，写清这段源码或这个 demo 对应哪个概念，不在两边重复写。例：`学习/PyTorch` 的训练循环 demo 指向 `知识/机器学习/Gradient Descent`。

`学习/` 不设固定子目录，形状由被拆的系统决定。它的两副骨架（拆源码的研习变体、练用法的练习变体）、配图约定、验收清单和方法页指路都在 `学习/学习.md`，**往 `学习/` 写之前先读它**。

`asset/images/` 放正文引用的图片，不是内容区。沉淀五区的图片一律落在这里，正文从仓库根写起引用（`![](asset/images/…)`，链到 `asset/` 下别的附件也一样），不写 `../`，不留原站外链；附件指到 `raw/` 或相对路径，`wiki check` 报错（素材图要用就复制进 `asset/`）。代价是 VS Code / Typora / GitHub 的预览显示不出这些图，图在 DSH 插件里看。旧的 `../asset/…` 写法会被 `wiki check` 当成没人引用而报出来。素材图不进 `asset/`，随素材走：书图放 `raw/book/<书名>/images/`，章节从 `../images/…` 相对引用；文档一篇 = `raw/document/<日期>/<文章名>/` 一个文件夹，md 与 `images/` 同住其中，正文相对引用（`images/…`）。

五区目录和文件名一律中文，专有名词除外。`raw/`、`asset/` 和工具目录用英文。区的先后在 `.wiki/wiki.json`。

## 三条规则

**规则一 · 按需生长**：没有子页的节点是平铺的 `X.md`；长出子页后变成 `X/X.md`，文件名不变（要改指别的文件，改 `X/.folder.json` 的 `index`；每个文件夹都有 `.folder.json`、列全子项、字段全部必填，由 `wiki page` 命令维护——绕开命令改了目录要手改，见 [ordering.md](ordering.md)）。五区任意深度都这样；`raw/book/` 的书页是 `<书名>/<书名>.md`。搬移用 `wiki page grow`，不手动做。

```
架构设计/
├─ 架构设计.md                ← 这一层的正文
├─ 电商系统架构设计/           ← 有子页了，收进文件夹
│  ├─ 电商系统架构设计.md
│  └─ 订单系统.md
└─ 库存系统架构设计.md         ← 没有子页，保持平铺
```

**规则二 · 固定骨架**：`经历/` 下固定 `观察/ 实践/`，`认知/` 下固定 `见解/ 方法论/ 原则/`，`系统/` 二层按名字分级：域级（名以「平台」收尾）固定 `业务域规划/` 与 `业务域落地/`，系统级（名以「系统」收尾）固定 `系统域规划/`——域级规划答整摊往哪走、系统级规划答这个系统往哪走，两级不同名；行业矩阵（名以「矩阵」收尾）不钉骨架：串联多个平台/系统、直接对应一个行业的信息化建设，不走平台/系统两级谱系，平台仍平铺在 `系统/` 二层、不挂矩阵下（先例：`系统/教育行业矩阵`；命名规范见 `系统/系统.md` 名词四级，先例长成见 `系统/系统.md`「行业矩阵在四级之外」）。骨架内部走规则一。定义只有一处：`repo.skeleton_for`。类目必须是文件夹页：`wiki page new <目录>/<类目>` 建出的是平铺 md，要再 `wiki page grow <目录>/<类目>.md`。建新业务域：`wiki page new 系统/<平台> <名>` 建域页（名以「平台」收尾），再对 `业务域规划` 与 `业务域落地` 各跑一遍 page new + page grow，`业务域落地/` 下设 `项目树/`（同样 page new + page grow）；建单系统：`wiki page new 系统/<系统> <名>`（名以「系统」收尾），下设 `系统域规划`（同样 page new + page grow）；用户故事不铺在门面层，建在对应的系统或域内部（判据见下表）。`wiki init` 建库时已铺好 `经历/`、`认知/` 的类目；缺了 `wiki check` 报「骨架：」，照同样的建法补。

系统区的平台节点固定骨架含 `业务域落地/`，下设 `项目树/` 收落地项目清单——落地与规划有差距，怎么向规划靠拢由人决策；项目树暂无项目也先立页。用户故事不铺在门面层，建在对应的系统或域内部。先例：`系统/人力资源平台/业务域规划/` 下挂八域设计页，`业务域落地/` 下挂 PeopleSoft系统、Medusa系统与项目树；`系统/支付平台/业务域落地/` 只有项目树一张。`Medusa系统/` 内有用户故事页，`业务域规划/招聘域/` 内有用户故事文件夹。单系统节点（OA系统、数据分析系统）钉 `系统域规划/`，不设落地抽屉。

骨架类目的判据只写在这里，不抄进骨架页正文：

| 类目 | 放什么 | 和邻居的区别 |
|---|---|---|
| `认知/见解/` | 理解、判断、心智模型 | `知识/` 说「领域是这样」，见解说「我认为是这样，因为……」 |
| `认知/方法论/` | 可复用的流程与套路 | 方法论答「怎么做」，原则答「做不做」 |
| `认知/原则/` | 取舍依据 | 同上 |
| `经历/观察/` | 我看到、听到的：会议、听录、外部文档、别人的分享。按月一个文件夹 `YYYY-MM/`，一次一篇 `YYYY-MM-DD-<标题>.md` | 主角是别人或外部；认知的来料 |
| `经历/实践/` | 我亲手做的事与过程。分法同观察 | 主角是我；认知的来料 |
| `系统/<平台>/业务域规划/`（固定骨架） | 域摊要做成什么样、怎么分阶段 | 规划答「整摊往哪走」，与系统级的系统域规划分开叫 |
| `系统/<平台>/业务域落地/`（固定骨架） | 域内已建/在建系统的落地现状 | 规划答「往哪走」，落地答「现在到哪了、差多少」；怎么靠拢由人决策 |
| `系统/<平台>/业务域落地/项目树/` | 落地摊的项目清单 | 项目树答「手上有哪些建设件」，随落地不随规划，暂无项目也先立页 |
| `系统/<系统>/系统域规划/`（固定骨架） | 本系统的规划：痛点、战略、路线与台账 | 答「这个系统往哪走」，不混叫业务域规划 |
| 系统或域内部的 `用户故事`（惯例，非固定） | 对应系统/域的具体需求故事 | 故事跟着系统走：已建系统放 `业务域落地/<系统>/` 内，规划中的域放 `业务域规划/<域>/` 内 |

**规则三 · 素材与沉淀分离**：`raw/` 永不编辑、永不重组（唯一例外：仓库级的路径约定变了，可以机械替换素材里的附件路径前缀，正文一字不动）。五区的页用 frontmatter 的 `source` 指回素材；一份素材可以沉淀到多个节点，不复制文件。素材身上不带状态，到达时刻和沉淀状态由命令现算，见 [sources.md](sources.md)。

仓库里不留示例页和脚手架，每一页都是真内容；演示规则写在本技能里。

## 定落点

一份内容进来，按三步定位置。素材的标题和章节不决定任何一步。

**一 · 分区。** 按内容性质分到系统 / 知识 / 学习 / 认知，经常同时占几个区；会议、听录、分享这类经历先落 `经历/`，再由人指定往哪沉淀。例：《电商系统设计与实现》的业务形态进 `知识/电商行业`，系统建设进 `系统/订单系统`，第 2 章拆成两半分别进这两处。

**二 · 门面还是细节。** 每个域的门面（`知识/<域>` 的同名页、`系统/<域>/<域>.md`）收全景与术语，它们是读任何细节页的前提。术语多到压过全景时，放进门面末尾的「附录」，或拆成门面下的 `<域>术语` 子页，按概念分组（动作、产品、机构……不照搬素材的分类），机构、制度这类有关联的组先画关系图再列表；门面首段链过去。细节等真要展开时才建节点，不建空壳。例：电商的全景在 `知识/电商行业/电商行业.md` 与 `系统/订单系统/订单系统.md`，词表在 `知识/电商行业/电商术语.md`；履约、促销学到那章再建。

**三 · 挂在哪个节点。** 问两个问题：

- **分解轴还是横切轴？** 分解轴答「分成几块」（流量 / 产品 / 转化），横切轴答「每块都要过的那层」（度量、信任、口径）。横切轴不挂在某个分支下，否则读者会以为它归那个分支管；已有一页且还会长的，立节点收拢。例：`知识/零售行业/电商/增长引擎/运营指标体系/`。
- **外延盖住几个邻支？** 只盖一个就进那个分支；盖住几个就放到公共父层平铺。例：OMO 同时含线上线下，住 `知识/零售行业/OMO.md`，不进 `电商/`。

## 双链

- 双链只写在沉淀区（经历 / 认知 / 学习 / 知识 / 系统），也只指向沉淀区的页。素材、书不用双链：路径写进 frontmatter 的 `source`，正文写纯文字。
- 页名全库唯一时写 `[[页名]]`；重名时写从区根起的路径 `[[系统/支付系统/项目树]]`（不带 `.md`，文件夹页写到文件夹为止），展示仍是页名。`#锚点`、`|标签` 照旧接在后面。
- 不确定是否重名，写路径形式总是对的。`wiki check` 报「同名歧义」时照候选改成路径形式。
- `wiki page new` / `wiki page move` 造出重名时会自动把原来的裸链改成路径形式，不用手改。

命令用法与什么场景选哪条命令，见 [commands.md](commands.md)。

## 注意

- 不开分支、不开 worktree，直接提交到 main，没有远端，不 push。别的技能要求开分支时以这条为准。
- 改结构一律走命令，不直接 `mv` / `mkdir` / 手写 frontmatter。
- 改完跑 `wiki check`，非零退出就是有问题。
- `wiki page move` 不改 `title`，需要时手动改。
- `wiki page move` 的路径写法分两种：文件夹页（`X/` 目录，即 `X/X.md` 那种带子页的节点）不带扩展名；叶子页（文件夹里的子页）的路径**必须带 `.md` 后缀**——不带会静默失败（报错走 stdout、退出码非零），串联跑多条 move 时容易漏看，每条之后用 `test -f` 目标路径确认落位。
- 规则本身的唯一来源是插件包 `vault-tools/lib/core/repo.py`（`.wiki/bin` 软链的指向处），改代码前读包内 `vault-tools/README.md`；vault 里没有代码副本，插件更新时随之更新。
