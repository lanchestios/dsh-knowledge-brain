## 定义

质量属性驱动设计是一套把性能、可用性、可修改性等质量要求写成具体场景，连同功能需求与设计约束比较架构候选，再落实为元素职责、接口及验证条件的方法。它用业务目标、设计代价与证据解释结构选择。

“高性能”“易扩展”只给出方向。能用于设计的要求还须说明谁在什么环境下施加什么刺激、系统如何响应，以及用什么度量判断响应是否可接受。

### 适用任务

| 任务 | 要解决的设计问题 |
|---|---|
| 新系统初步设计 | 哪些要求真正影响结构，先解决什么？ |
| 多个技术方案难取舍 | 候选各改善什么、牺牲什么，依据是什么？ |
| 已有系统局部重构 | 当前元素怎样改变才能满足关键场景？ |
| 设计评审 | 结构、接口与关键要求之间能否追溯？ |

### 必要输入

| 输入 | 最低要求 |
|---|---|
| 业务目标与优先级 | 干系人说明哪些结果更重要及其理由 |
| 功能需求 | 关键任务、正常与异常行为，允许尚有缺口 |
| 质量需求 | 具体场景、响应度量及测量条件 |
| 设计约束 | 必须遵守的技术、集成、资源或交付条件 |
| 当前设计 | 待分解元素、职责、依赖及已作出的决定 |

## 出身

SEI 的 QAW 第三版发表于 2003 年，用跨角色工作坊在架构完成前发现、排序并精化质量场景。Wojcik 等人在 2006 年发布的 ADD 2.0，则以需求驱动递归分解系统元素，形成角色、职责、关系与接口。

Kazman 等人在 2000 年的 ATAM 报告中，强调识别架构决策的风险、敏感点与权衡，而不把早期架构分析当成精确质量预测。

## 核心构件

### 场景要素

QAW 与 ADD 2.0 使用的六项信息把质量要求变成可讨论的刺激—响应关系。

| 要素 | 必须回答 |
|---|---|
| 刺激源 | 谁或什么发起事件？ |
| 刺激 | 发生什么请求、故障、变化或压力？ |
| 受刺激构件 | 哪个系统或元素受到影响？ |
| 环境 | 负载、运行模式及其他成立条件是什么？ |
| 响应 | 系统应如何处理？ |
| 响应度量 | 多快、多少、损失多少或需多少工作量？ |

### 设计链条

| 构件 | 作用 |
|---|---|
| 候选架构驱动 | 结合业务重要性与结构影响，选定本轮关注的要求 |
| 设计关切 | 将驱动落到需要处理的设计问题，如故障检测与恢复 |
| 候选设计概念 | 比较模式、战术及其组合的优缺点与区分参数 |
| 元素与接口 | 明确职责如何分配、如何交互、依赖哪些条件 |
| 验证与追溯 | 让场景、选择理由、结构及待取证事项互相对应 |

Sensitivity Point（敏感点）是影响某项质量响应的关键架构属性；Tradeoff Point（权衡点）同时影响多项属性。讨论一个候选的收益时，也应追问它对其他重要场景的代价。

### 取舍示意

以下为原创候选比较，只有方向性判断，尚不构成实测结论。

| 设计关切 | 每次现算 | 预先计算 | 待取证条件 |
|---|---|---|---|
| 查询响应 | 取决于计算与并发成本 | 可能降低查询工作量 | 代表数据与峰值请求下的响应 |
| 结果新鲜度 | 查询时取当前输入 | 依赖更新周期 | 业务能接受的最大滞后 |
| 变更成本 | 修改计算路径 | 还需处理旧计算结果 | 规则变更后的重算范围 |

若响应与新鲜度目标冲突，应由干系人确认取舍或补充设计；不能用“上缓存”掩盖尚未决定的业务条件。

## 操作规则

### 分析步骤

1. 确认需求信息足够。同时核对功能、约束与质量要求。与干系人澄清场景和业务优先级；未排序的要求退回排序，暂定要求及其影响的决定作标记。
2. 选择待分解元素。明确本轮处理整个系统还是某个元素，并列出它已承担的需求、职责及外部依赖。
3. 识别候选架构驱动。在业务重要性之外评估对结构的影响，选少量关键要求聚焦；分析发现影响判断有误时，允许增删候选。
4. **选择设计概念。** 先列设计关切，再列能处理它的模式或战术。按驱动比较优缺点、区分参数、组合与互斥关系，记录选择理由并检查元素间的一致性。
5. 实例化元素并分配职责。根据候选概念确定具体子元素；用功能场景走查，保证父元素每项功能能由子元素的职责序列表达。
6. 定义接口。沿场景核对输入、输出、交互关系、异常、所需数据及质量条件；不要只给出接口名称。
7. 验证并细化需求。检查分解是否满足功能、质量和约束，将需求分配给子元素并细化；证据不足处使用模型、实验、仿真或评估继续取证。
8. 选择下一元素重复。将本轮结果作为后续约束。新证据推翻假设时，回到相关需求或候选，修订受影响的设计。

架构尚未成形时，可借 QAW 的方式邀请多类干系人贡献预期使用、增长及意外压力场景，再合并、排序、精化。场景表达比争论它属于哪种质量属性更重要。

### 最小产出

| 产物 | 最低内容 |
|---|---|
| 驱动场景表 | 六要素、业务目标、优先级、暂定项与目标依据 |
| 候选比较表 | 驱动、候选、区分参数、收益、代价、假设与选择理由 |
| 设计说明 | 本轮元素、职责、关系、接口及必要的结构视图 |
| 追溯与验证表 | 场景对应的设计、已知证据、未决风险及下一项验证 |

无法靠现有分析区分候选时，通过[[风险驱动的方案验证]]取得证据。选择及其理由可以记录为架构决策，但记录本身不替代设计分析。

### 验收判据

- 关键质量目标具备具体场景与响应度量，数值依据和环境条件可见。
- 候选驱动来自功能、质量与约束的共同考虑，且有业务与结构影响的排序理由。
- 候选比较写明跨属性代价和未验证假设，不只列所选技术的优点。
- 子元素的职责能完整解释父元素的功能，接口足以解释交互与异常。
- 每个关键场景都有对应设计和验证状态；未满足、待取证与暂定项没有被表述成已通过。

## 可信边界

设计流程以 ADD 2.0 八步为依据；工作表、取舍示意及方法间的串联是作者归纳，不冒充 ADD 3.0 的步骤。QAW 可以帮助获得优先场景，ATAM 也能帮助评估，但后者不是 ADD 输入排序的唯一来源。

六要素让需求具体，不保证目标数值合理。原报告允许需求不完整并要求标明暂定决定；条件改变后仍须回看设计。早期分析和方向性比较不能证明生产达标，ATAM 中的非风险判断也只在原假设继续成立时有效。
