一套把产品战略拆成可开发需求的梳理法：**战略 → 流程 → 三层用例 → 执行过程与交互过程 → 信息结构**。

它要解决的问题**不是「需求对不对」，而是「需求全不全」**。一个核心系统一旦漏了环节，上线后的问题会迅速升级：交易平台加一种新商品类型，不只要考虑生单、支付、退款，还要考虑数据统计、财务确收、监管上报、履约、解约，最后还得给客服和运维留排查功能。漏一处，代价在上线之后才付。

这不是 Domain-Driven Design，两者切入点相反——见文末「与 DDD 的关系」。

## 方法衔接

流程与用例分析属于 [[系统分析与设计]]，从 [[问题界定与需求发现]] 确定的用户目标与问题证据出发。三层用例用来核对目标、实现途径与跨系统步骤；[[产品功能拆法]] 再按能力组织功能，[[用户故事写法]] 再按独立用户结果切片并定义验收。

流程覆盖检查与 [[领域建模与边界划分]] 相互校验：流程解释行为，领域模型解释概念与规则。功能组织、故事切片与实施任务各有不同粒度，不要求每个步骤单独成为一条故事。

## 五步

### 一 · 战略拆成流程

从产品战略的每条目标出发，拆成一条条端到端的业务流程。判据是**这条流程能不能一句话说完，且说得出起点与终点**。

### 二 · 流程拆成三层用例

| 层次 | 描述什么 | 例子 |
|---|---|---|
| **目标层用例** | 用户使用系统的根本目标 | 用户购课 |
| **实现层用例** | 用什么途径达成这个目标 | 老师在 B 端帮家长挑商品并下单，家长只需付款 |
| **步骤层用例** | 执行时的具体步骤，以及每一步落在哪个系统 | 创建用户《用户系统》→ 选商品《商品系统》→ 生成订单《订单系统》→ … |

配套要先做两件识别：

- **识别参与人**：家长、老师、财务、第三方监管——**分角色画泳道**，谁的动作归谁
- **识别参与系统**：用户、商品、订单、支付、履约（课程/发票/合同/物流）、业绩、财务、监管、短信

**三层的价值在于分离关注点**：目标层用来对齐要不要做，实现层用来对齐怎么做，步骤层才开始牵扯系统边界。混在一起谈，会在还没确定要不要做的时候先吵起系统怎么拆。

**从实现层到步骤层的那一跳最值钱**：给每个步骤标上负责的系统之后，跨系统的通知与依赖会自己浮出来——付款完成之后要通知履约、业绩、财务、监管四方，这件事在实现层看不见，在步骤层藏不住。

### 三 · 描述执行过程

对步骤层用例结合真实场景细化。三条判据：

1. **区分参与人**。有协同操作时，每个活动都要标明谁在做
2. **过程闭环**。有支付就必须有支付之后的动作
3. **执行过程是给人看的，不是设计软件，也不是设计交互**。生成订单号、点按钮弹窗这类东西不画进去

第 3 条是最容易破的一条，破了之后这张图就变成了一张画得很差的设计稿。

### 四 · 描述交互过程

分两类关切；它们描述同一任务的不同方面，不按前后端划分需求：

| 层 | 关注什么 |
|---|---|
| **界面层** | 用户与 UI 的交互过程 |
| **规则层** | 流程的异常情况 |

围绕「参与者操作 → 系统动作 → 系统反馈」写清正常与异常结果。字段校验等细节只在影响业务结果或验收时展开，共同规则引用同一维护处。

### 五 · 共识信息结构

产品与研发一起做，四步：

1. 梳理出所有的实体
2. 梳理出数量关系
3. 明确信息的属性
4. 考虑效率和灵活性

顺序值得注意：**先关系、再属性、最后才谈效率**。反过来做（先看表怎么建得快）会把业务关系扭曲成存储方便的形状。

## 一条判据：产品需求还是用户需求

用户需求说明角色希望达成什么与为什么；产品需求进一步明确系统行为、规则、边界和验收，使开发者能据此实施。

讨论卡住时，先判断缺的是用户目标还是可实施定义，再补对应内容。能指导开发仍不等于可以排期；规模、依赖、资源、权限与风险的判断归 [[系统知识建设推进]]，故事切片与验收归 [[用户故事写法]]。

## 与 DDD 的关系

两者切入点相反，**不是替代关系**：

| | 流程与用例驱动 | Domain-Driven Design |
|---|---|---|
| 起点 | 用户目标与业务流程 | 领域知识与领域专家的理解 |
| 强项 | 检查需求覆盖，减少环节遗漏 | 澄清领域语义，明确模型边界 |
| 产出 | 用例、执行/交互过程、信息结构 | Ubiquitous Language（通用语言）、Bounded Context（限界上下文）、聚合 |

**它们衔接在第五步**：这里产出的「实体 + 数量关系」正是 DDD 建模的输入，实体 与 值对象 的分辨、聚合 边界的划定都从这里开始。

**要注意的一处偏差**：把 DDD 理解成「跟随行业优秀实践」是错的——Core Domain（核心域）按定义是**使你与竞争者不同**的那部分，判据是「需要保密以保持竞争优势的就是核心域」。跟随行业最佳实践的东西，按定义属于通用子域。详见 子域。

## 可信边界

**流程覆盖检查不能自证需求完整，也不能保证模型好。** 按流程和用例一路拆下来，很容易得到一份「照着界面长出来的」信息结构——实体是屏幕上要显示的东西，而不是业务本身的概念。这正是 DDD 要治的病。第五步做完之后应该再过一遍领域视角，并用真实场景、参与方与异常结果抽查遗漏。

**三层用例的层次划分依赖判断力。** 「目标」与「实现」的界线在复杂业务里会模糊：老师帮家长下单，究竟是实现途径还是另一个目标？划错会把该对齐的东西跳过去。

**它对「变化」无话可说。** 整套方法处理的是「这一版要做什么」，没有回答「下一版改起来贵不贵」。可改性那一半得靠 DDD 那边的构件。
