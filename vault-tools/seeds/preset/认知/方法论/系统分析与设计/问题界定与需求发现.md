## 定义

问题界定与需求发现是一套在承诺建设前，查清谁在什么情境下受阻、当前代价是什么、哪些改变值得继续调查的方法。它把预设功能还原为用户要完成的任务，以事实、假设和约束支持下一步投入决定。

发现需求时，既要听参与者如何解释工作，也要核对他们实际如何完成工作。提出“要一个系统”只能说明有人提出了解法，尚不能说明问题、受益者与成功标准已经清楚。

### 适用任务

| 任务信号 | 需要回答的问题 |
|---|---|
| 接到产品或建设指令 | 为什么需要它，谁会因此更容易完成任务？ |
| 多方对范围争执 | 各自要改善哪段工作，谁能决定边界？ |
| 老系统抱怨很多 | 阻碍来自功能、信息、流程还是协作？ |
| 需求不断追加 | 哪些支持同一目标，哪些其实属于另一问题？ |

### 必要输入

| 输入 | 最低要求 |
|---|---|
| 初始诉求 | 保留提出者、原话与期望改变，允许它只是方案 |
| 任务参与者 | 能接触用户、运营人员及相关流程的责任人 |
| 现状材料 | 近期实例、工作记录或可观察的任务过程 |
| 调查边界 | 负责人、可用时间、可访问材料与保密限制 |

## 出身

GOV.UK 的 discovery 实践要求在建设服务前理解用户目标、政策意图、约束及改善机会；调查结束时判断是否值得继续探索，也允许停止。它要求质询预设方案，并共同确定哪些事项不属于当前问题。

Eric Evans 在 2003 年的 Domain-Driven Design 中，通过开发者与领域专家共同走查印制电路板场景，展示了如何纠正术语、发现真正关心的行为，并用简化原型检验理解。专家要求的报告形式，并不等于他们最终要解决的问题。

## 核心构件

| 构件 | 记录内容 | 用来防止 |
|---|---|---|
| 问题陈述 | 人群、情境、任务、受阻与代价 | 把功能名称当问题 |
| 现状旅程 | 任务起止、参与者、渠道、交接与等待 | 只看团队控制的一小段 |
| 证据台账 | 观察或记录、来源、适用范围、反例 | 把一位参与者的意见当普遍事实 |
| 约束清单 | 约束依据、可改程度、责任人 | 把惯例当不可改变的规定 |
| 假设清单 | 尚未成立的判断、影响与取证办法 | 把未知埋进方案 |
| 退出决定 | 继续、改向或停止及理由 | 调查无限延长 |

证据与解释分开记录。例如，“三次预约都重复填写住址”是观察；“共享信息会减少放弃”是待检验的解释。对相反实例也保留记录，不能为了简报整齐而合并掉差异。

### 改写示意

以下为原创情景。

| 表达 | 它允许调查什么 |
|---|---|
| 建一个预约小程序 | 只指定了交付物，尚无问题范围 |
| 让上班族更容易约到晚间窗口 | 开始能找用户和任务，但受阻原因未明 |
| 下班后办理者找不到仍可预约的窗口，反复电话询问 | 可观察查找过程，核对信息、窗口供给与交接 |

若主要障碍是窗口根本没有晚间供给，新增入口就不能单独解决问题；应把供给调整或停止该方案纳入候选。

## 操作规则

### 分析步骤

1. 约定发现目标。写明这轮需要支持什么决定、由谁作出、哪些问题暂不研究。结束条件以所需认识为准，不把固定周数当完成标志。
2. 拆开预设方案。追问受益者、触发情境、想完成的任务和当前困难；把功能承诺改写为问题，另列不在范围内的事项。
3. **走查实际任务。** 请参与者带着最近实例，从触发到结果逐步复述或演示。记录渠道、交接、异常及返工，补访线上流程之外的运营人员。
4. 核对差异与证据。比较不同用户、数字能力、无障碍需要和任务条件；将共同问题、特定人群问题与个别意见分开，标出未覆盖人群。
5. 调查代价与约束。核对时间、失败、重复劳动等现状代价及其口径。对法律、合同、遗留技术和流程惯例分别问依据、可改程度与改变责任人。
6. 比较改善方向。至少考虑建设功能之外的可行改变，如改内容、调整线下流程、复用已有服务或协作；说明每个方向依赖什么假设。
7. 形成退出决定。依据潜在改善、投入和约束，决定继续、改向或停止。继续时选出最先应验证的假设，并明确成功如何测量。

当专家纠正术语或说“实际并非如此”时，回到具体例子修订理解。没有证据消除的分歧应保留为假设，不以会议上的默认同意替代核对。

### 最小产出

| 产物 | 必须能读出的内容 |
|---|---|
| 问题简报 | 谁、何时、要完成什么、受阻、代价、边界与决策人 |
| 现状草图 | 任务起止、线上线下渠道、参与组织与关键交接 |
| 证据台账 | 每项判断的依据、覆盖人群、反例和未知 |
| 约束与假设表 | 不能改与可能改的条件、责任人、最先验证什么 |
| 退出记录 | 继续或停止的理由、候选改善、下一步资源与成功指标 |

继续投入时，按[[风险驱动的方案验证]]验证假设；需要统一业务含义时，再进入[[领域建模与边界划分]]。问题尚未清楚时，不以更细的功能规格代替问题调查。

### 验收判据

- 不看功能名称，也能说清目标用户、任务、受阻和为什么值得改善。
- 范围包含必要的跨组织与线下交接，并明确本轮不负责什么。
- 重要判断能追溯到观察、记录或明确标出的假设，反例与未覆盖人群可见。
- 现状代价、成功指标与未来取数办法有口径；查不到基线时明确保留未知。
- 已比较可行改善方向，退出决定能解释为何继续、改向或停止。
- 继续时知道第一项要验证的假设、需要谁参与及谁负责下一步。

## 可信边界

上述步骤、问题简报、台账表头与示意是作者结合材料的归纳，不是 GOV.UK 或 Evans 原文提供的一套同名模板。GOV.UK 的阶段、审批与常见时长属于英国公共服务交付语境，不能直接充当所有团队的制度。

材料没有提供访谈抽样、观察偏差控制或因果判定算法。完成表格只能使判断与未知可见，不能证明所有需求真实、改善一定由系统引起；样本偏向、利益冲突及无法接触的用户仍会限制结论。

专家共建模型有助于理解行为，但并非每次发现工作都需要先建对象模型。目标、任务或约束改变后，应重新核对问题边界；硬约束使改善无法成立时，停止是有效产出。
