## 定义

系统演进与迁移设计是一套把现状到目标的改变拆成可交付单元，并为每个单元说明新旧如何共存、使用方如何迁移、失败如何处置以及何时删除旧结构的方法。它设计的是一段有中间状态的变化过程，使业务收益、过渡成本与风险能够逐批评估。

目标结构只描述最终想要什么。迁移设计还必须回答过渡期谁提供服务、谁拥有数据与规则、调用走哪条路径，以及哪些改变已经无法靠切回旧程序恢复。

### 适用任务

| 任务 | 设计重点 |
|---|---|
| 替换嵌入日常业务的遗留系统 | 找到可隔离的小块与可交付收益 |
| 修改不兼容的接口 | 让旧、新使用方在迁移期都能工作 |
| 调整系统或模型边界 | 明确跨界含义、所有权及转换职责 |
| 更新数据结构或运行平台 | 调查兼容条件、切换状态与恢复限制 |

### 必要输入

| 输入 | 最低要求 |
|---|---|
| 业务结果 | 为什么改变、哪些旧行为应保留或不再需要 |
| 现状依赖 | 调用方、批任务、人工流程、接口、数据与实际责任人 |
| 目标差异 | 行为、模型、接口和运行条件将改变什么 |
| 运行约束 | 可中断范围、发布能力、可观测条件与维护资源 |
| 数据与副作用 | 写入权、历史数据、外部动作及可能不可逆的转换 |

## 出身

Martin Fowler 的 Strangler Fig 实践主张渐进替换遗留行为，通过接缝将小块隔离，并接受最终会删除的过渡架构成本。他强调业务结果、拆分、交付和组织改变需要共同推进，所列四项活动没有固定先后顺序。

Danilo Sato 在 2014 年的 Parallel Change 中，把不兼容接口改变明确分为 expand、migrate、contract 三阶段。供应方先同时支持新旧接口，使用方逐步迁移，最后移除旧接口和闲置结构。

Eric Evans 在 2003 年的 Domain-Driven Design 中要求先描绘实际模型上下文及接触点，再做改变。这为迁移前调查语义、所有权与转换边界提供依据。

## 核心构件

| 构件 | 必须说明什么 |
|---|---|
| 迁移单元 | 可隔离的一块业务行为、使用方及独立收益 |
| 接缝 | 在何处隔离或转接行为，谁控制该位置 |
| 过渡架构 | 新旧协作方式、兼容与转换责任、最终删除对象 |
| 状态与门槛 | 每个阶段谁在工作、何时进入下一阶段 |
| 恢复边界 | 能切回什么、不能撤销什么、如何恢复或补偿 |
| 收缩证据 | 旧使用已消失与旧结构可移除的依据 |

迁移单元应从业务行为与依赖中寻找，不能只按新技术目录划块。若一块仍依赖大量未识别的共享写入或隐蔽调用，应先补调查或插入接缝。

### 状态示意

以下为原创“查询接口替换”情景；状态门槛是项目控制措施，不是来源原有的验收表。

| 状态 | 运行形态 | 前进门槛 | 失败处置边界 |
|---|---|---|---|
| 现状 | 使用方只访问旧接口 | 新旧语义、依赖与责任人已核对 | 继续维持旧路径 |
| 扩展 | 供应方同时支持旧、新查询 | 旧行为兼容，新查询具备验证证据 | 停用新入口，前提是无额外不可逆动作 |
| 迁移 | 分批使用方切到新查询 | 每批结果、异常与剩余使用方可见 | 未收缩前可按兼容条件切回 |
| 收缩 | 只保留新查询，删除旧入口 | 旧调用已完成迁移且收缩证据获确认 | 恢复旧入口需重新发布并重新核对兼容 |

“入口能切回”只描述路由能力。若同时发生新格式写入、丢失信息的转换或外部扣款等动作，切回程序不会自动撤销这些结果，必须另外判断恢复或补偿路径。

## 操作规则

### 分析步骤

1. 核对现状与结果。沿实际业务任务盘点调用、数据、批处理和人工操作，明确控制权与依赖；写清期望业务结果及不应照搬的旧行为。
2. 挑选迁移单元。比较每块的收益、依赖与隔离成本，优先选择能够形成闭环交付的部分；尚无接缝时，先设计必要的隔离与转接。
3. 设计共存状态。列明新旧接口、模型含义、转换、读写责任和使用方路由；为每种兼容组合注明支持范围及必须验证的条件。
4. **约定门槛与恢复。** 对每次切换写明观察指标、停止条件、可恢复的状态及不可逆动作。恢复依赖备份、数据转换或补偿时，先验证这些能力，不以“可回滚”概括。
5. 扩展并验证兼容。先让供应方具备必要的新旧支持，核对旧使用方行为不被破坏；未证明兼容或数据条件成立时，不推进迁移批次。
6. 分批迁移使用方。按可识别的人群或调用方切换，每批观察任务结果与异常，并更新已迁、未迁和未知使用方清单；必要时暂停、修订或按有效恢复路径退回。
7. 确认后收缩。依据使用观测、责任人确认与约定窗口核查旧依赖；满足门槛后删除旧入口、闲置结构和过渡机制，核对业务与运行结果。
8. 回看后续单元。把依赖发现、兼容问题和运行结果用于下一批计划；同步检查组织与开发实践，避免新结构重复形成旧有僵化。

### 数据条件

| 待验证事项 | 推进前必须回答 |
|---|---|
| 新旧读写共存 | 谁是权威写入方，部分失败、冲突和旧客户端如何处理？ |
| 历史数据移动 | 回填期间新增或修改的数据如何识别，遗漏如何发现？ |
| 重试与顺序 | 重复、乱序、删除和失败重放会不会改变业务结果？ |
| 切换核对 | 用什么业务口径检查差异，哪些差异阻止继续？ |
| 不可逆转换 | 丢失的信息是否能重建，外部副作用能否补偿，由谁执行？ |

这些是迁移方案的待验证条件，不是一套已解决一致性的数据协议。遇到不明确的答案，应先做专项设计与[[风险驱动的方案验证]]，不能从“采用渐进迁移”推断数据必然正确。

### 最小产出

| 产物 | 最低内容 |
|---|---|
| 现状与目标说明 | 业务结果、实际依赖、语义差异、所有权及不保留的行为 |
| 单元与状态表 | 切片、共存形态、兼容条件、使用方和每次转换的负责人 |
| 批次与恢复计划 | 每批门槛、停止条件、可恢复状态、不可逆限制及证据 |
| 收缩清单 | 旧调用、旧数据结构、过渡机制、删除依据与剩余未知 |

### 验收判据

- 每个迁移单元能解释业务收益、依赖与隔离方式，并有明确责任人。
- 每个中间状态的服务提供者、调用路径、语义和数据责任都可读。
- 各批切换有证据门槛、观察与停止条件；恢复计划说明能力限制而非只写“回滚”。
- 数据共存、历史核对和不可逆副作用已有专项证据，未解决项会阻止相应推进。
- 收缩基于已迁移使用方清单、实际观测与责任人确认，观测窗口及盲区可见。
- 旧结构与过渡机制有退出条件，完成后重新核对关键业务和运行结果。

## 可信边界

完整分析步骤、状态表、数据问题与收缩门槛是作者的归纳。Parallel Change 的三阶段有序，Fowler 所列四项现代化活动无固定顺序；不能把它们合成原作者提供的统一阶段算法。

来源没有完整解决数据库双写、回填、去重、顺序、历史核对和切换演练协议，也没有证明隐蔽调用可被完全观测。兼容与收缩结论只覆盖已核查范围，仍需为盲区保留责任与处置办法。

渐进替换可以降低单次变更风险并提前交付价值，但共存成本可能很高，小系统未必合算。不可逆写入、信息丢失或外部副作用发生后，可能只能恢复到另一可接受状态；没有证据时不能承诺原状恢复或随时回滚。
