## 定义

领域建模与边界划分是一套让领域专家与开发者借助真实业务实例，形成一致术语、行为和规则，并确定这些解释在何处有效的方法。它分别回答业务如何分解、模型在哪保持一致、模型之间如何协作，为边界调整提供可核查的依据。

模型只保留解决当前问题所需的知识，不必复制业务世界的一切。判断模型是否有用，要看参与者能否用它解释任务、预测行为并指出反例。

### 适用任务

| 任务信号 | 分析重点 |
|---|---|
| 同一词在团队间意思不同 | 找出不同定义、行为和适用条件 |
| 业务范围过大或投资分散 | 按业务能力分解，识别差异化价值 |
| 共享代码或数据经常互相破坏 | 核对模型是否实际一致、共享由谁维护 |
| 准备拆分系统或服务 | 先验证语义边界，再比较部署选择 |

### 必要输入

| 输入 | 最低要求 |
|---|---|
| 问题与范围 | 要支持的业务任务、明确排除的事项 |
| 专家与实例 | 能解释正常、异常和边界情形的参与者及记录 |
| 现状结构 | 系统、接口、数据库、团队及实际控制权 |
| 规则依据 | 业务规定、代码行为或运营习惯，注明相互冲突处 |

## 出身

Eric Evans 在 2003 年的 Domain-Driven Design 中，把知识获取、共同语言与模型实验结合起来，并用 Bounded Context（限界上下文）限定模型的有效范围，用 Context Map（上下文图）描述实际模型之间的接触与转换。

Vaughn Vernon 在 2016 年的 Domain-Driven Design Distilled 中，以 Subdomain（子域）分解业务问题空间，区分应当重点投资的业务能力与可采用现成方案的能力。他建议尽量让一个模型上下文对应一个子域，也承认遗留现实可能做不到。

这两种划分解决不同问题：业务分解帮助判断做什么及投入多少，语义边界帮助保持模型一致。两者还需要与实际软件结构核对。

## 核心构件

### 三种边界

| 划分对象 | 回答什么 | 不能直接推导什么 |
|---|---|---|
| Subdomain（子域） | 哪部分业务问题需要哪类专业知识和投资？ | 必须独立成一个服务 |
| Bounded Context（限界上下文） | 哪个范围内术语、概念与规则必须一致？ | 必须一队、一仓库或一次部署 |
| 服务与部署单元 | 哪些运行职责分别发布、扩缩与运维？ | 各单元必然使用不同模型 |

同一软件部署内可能纠缠多个业务子域与模型；多个团队也可能共同维护一个一致模型。文件夹、仓库或进程边界只是调查线索，不能代替语义证据。

### 建模记录

| 构件 | 必须留下什么 |
|---|---|
| 术语与规则表 | 含义、适用范围、行为规则、实例和反例 |
| 业务子域图 | 业务职责、专家、关联及投入依据 |
| 现状上下文图 | 实际模型、名称、接触点、转换与共享内容 |
| 候选边界表 | 调整理由、保留内容、跨界协作及维护代价 |
| 核查场景 | 能揭露含义冲突或跨界失败的具体任务 |

投资分类看业务价值：Core Domain（核心域）承载竞争差异；Supporting Subdomain（支撑子域）通常需要定制但不是核心差异；Generic Subdomain（通用子域）可采用现成方案，也可能由内部实现。提供者在组织内外不是分类依据。

### 边界示意

以下为原创情景：同一“客户”在两种模型中承担不同责任，部署形态另行决定。

| 层次 | 销售侧 | 交接 | 财务侧 |
|---|---|---|---|
| 业务问题 | 跟进购买机会 | 已成交事实 | 管理应收款 |
| 模型含义 | 客户可以尚无交易 | 识别谁是付款责任人 | 应收对象须有结算责任 |
| 设计候选 | 销售上下文 | 标识映射与语义转换 | 结算上下文 |
| 部署选择 | 可与财务同进程 | 仍须明确转换 | 也可独立发布 |

若直接共享一张“客户”表，双方仍须解释哪些字段和规则能够共同维护。名字相同不能证明是同一概念。

## 操作规则

### 分析步骤

1. 选择关键实例。从已界定的问题中选正常、异常与争议场景，请领域专家说明参与者、事件、结果及不可违反的规则。
2. **共同演练模型。** 用草图和术语叙述过程；发现图无法解释行为时，改概念、关系或规则。暂不纳入对当前目标无影响的知识。
3. 分解业务问题。按专业知识与业务职责识别子域，记录专家、依赖和价值。对投资类型给出业务理由，不能照技术复杂度自动分类。
4. 描出现状模型。核对团队实际用语、实现行为、数据库含义和控制权，命名模型上下文；把联系点、共享内容与转换责任逐项列出。
5. 提出边界候选。比较保持统一、修复混乱或分开模型的选择，说明各自如何处理概念冲突、跨界规则和协调成本。现状与目标分别表达。
6. 走查跨界任务。用同一实例让两侧独立解释输入、结果、标识与状态，检查转换后是否丢失业务含义，异常时由谁处理。
7. 修订模型并明确职责。重新建模以解释冲突，将不可确认的调用或规则留作待验证条件；边界接受后再比较服务与部署安排。

维护统一模型还需要持续沟通与集成检查。边界画出后无人维护术语、规则和共享内容，模型仍会再次分裂。

### 最小产出

| 产物 | 最低内容 |
|---|---|
| 模型实例集 | 任务、术语、行为规则、反例及专家反馈 |
| 子域清单 | 业务职责、专家、价值类别与判断依据 |
| 现状边界图 | 模型范围、所有权、接触点、转换和共享 |
| 候选边界说明 | 分合理由、跨界规则、代价、未知与核查结果 |

### 验收判据

- 关键场景能由专家与开发者使用同一组明确含义的术语解释。
- 每个候选上下文都有模型一致性依据，边界不是仅由组织、表名或代码目录推得。
- 跨界接触点能说明交换什么、转换什么、谁维护，以及失败由谁处理。
- 同名异义与重复概念已辨认；重要冲突已修正或明确保留为未决条件。
- 业务子域、模型范围与部署选择分别可读，现状没有被目标图覆盖。

## 可信边界

分析步骤、工作表、验收项与销售财务示意是作者归纳；它们不是原著的自动切分算法。材料没有提供边界粒度、所有权或事务约束的统一评分公式，具体取舍须由业务实例与运行事实检验。

子域与上下文一一对应是 Vernon 的设计建议，不能倒推所有遗留系统的现状。Evans 的货运例中有两支团队共同使用一个模型上下文，因此“一上下文只能一团队、一仓库”不构成普遍规则。

归档的 Vernon 译本含术语括注等 OCR 待核问题。边界清晰也不保证分布式事务、数据一致性或部署独立性已经成立，这些仍需另行设计与验证。
