接手一个已经在跑的内部系统，把它推成产品的做法。七个环节连成一条链：拆解现状 → 业务痛点 → 核心价值 → 产品战略 → 整体规划 → 项目树 → 用户故事。前一环的产出是后一环的输入，换顺序会让后面那环失去依据。

跟 [[系统架构拆解]] 的分工在终点：那套方法的终点是**看懂**，它要解决的是「我是不是在编」；这条链把看懂当作第一环的产出，终点是**排得出期**。

## 出身

从真实业务域的实际推进里提炼：前五环走完、各自成页，后两环没走完——`项目树/` 与 `用户故事/` 至今是空的。所以这条链的最后两环是照 [[流程与用例驱动设计]] 推出来的，没有经过实践检验。

## 七环

| 环 | 产出什么 | 这一环算完的判据 | 方法 |
|---|---|---|---|
| 拆解现状 | 系统当下是怎么造的 | 断言出自对账（代码、纪要、问人，见下）；不看源码能答出「改 X 会影响什么」 | [[系统架构拆解]] |
| 业务痛点 | 痛在哪几格 | 痛点按环节排出断点，每条标明承担者与喊痛者 | 见下 |
| 核心价值 | 哪些买得到、哪些买不到 | 两类分清，并说得出依赖方向 | 见下 |
| 产品战略 | 先做什么后做什么 | 实施顺序有论证，收益口径有纪律 | 见下 |
| 整体规划 | 分几层、层间什么关系 | 层与层的依赖方向明确，未定项显式列出 | 见下 |
| 项目树 | 手上有哪些项目 | 每个项目说得出起点与终点 | [[流程与用例驱动设计]] |
| 用户故事 | 具体要做什么 | 能指导开发的进排期，不能的继续拆 | [[流程与用例驱动设计]] |

两头借方法，中间四环是这条链自己的部分。

## 中间四环的判据

### 业务痛点

一条痛点至少记三样：断在哪个环节、谁在承担这个成本、谁在喊。

**承担者与喊痛者错位是常态**，而这个错位本身是论证材料：喊得最响的环节未必是成本最高的环节，成本最高的那个往往没人喊，因为承担的人没有话语权。把两者分开记，自下而上的实施顺序才有依据——否则排序会跟着嗓门走。

### 核心价值

把环节分成两类：市面上有成熟产品可以买的，和买不到只能自己建的。

判据不是「难不难」，是**换一家供应商能不能解决**。分完之后还要回答一个问题：买得到的那部分，能不能脱离买不到的那部分单独用。多数情况下不能——买来的工具依赖自己建的那层底子，而这个依赖方向决定了实施顺序。

### 产品战略

战略只回答两件事：先做什么后做什么，为什么是这个顺序。

收益口径有一条纪律：**不把收益折算成年化金额**。折算需要一串假设（人力单价、节省工时、采纳率），每个假设都可辩，而折算之后原始事实被一个精确的数字盖住了，讨论会转移到假设上去。记原始事实：省掉几次会议、几个人从几天变成几小时。

### 整体规划

分层图不是这一环的产出，**层与层之间的依赖方向**才是。同一张图，画成「每层只依赖下一层」和画成「三方互相通信」，推出来的契约设计完全不同。

这一环最容易出的问题是把没想清楚的地方用一张图糊过去。已知未定的东西单独列一节，列出来的每条要写清两种读法各自的后果——这样后面接手的人知道哪些是结论、哪些是待办。

## 内部拆解与外部拆解的差别

第一环用 [[系统架构拆解]]，但内部系统有三处不同，那页按外部系统写的行文覆盖不到：

| | 外部系统 | 内部系统 |
|---|---|---|
| 基线放哪 | 克隆进 `raw/project/`，被 `.gitignore` 挡在版本库外 | 不钉：活仓随开发在动，钉住的 commit 对写作没有意义；回验靠对账（见下） |
| 取材多哪几路 | 作者博文、被拒的 issue 与 PR | **问人**、评审纪要、需求文档 |
| 最大信息源 | 作者博文（代码只说结果，博文才说岔路口） | 人。作者就在隔壁，这是外部项目拿不到的一路 |

问人这一路要注意它的失效方式：口述的是当下的理解，不是当初的决定，而两者经常不一致。口述得到的取舍要回到代码或评审纪要里对账，落三类判定，跟其余五路一样处理。

## 顺序为什么不能换

三处换了就塌：

**拆解现状必须在业务痛点之前。** 现状没拆清就排痛点，会把现象当成因——「取数慢」是现象，慢在会议沟通还是慢在加工链，是两个完全不同的痛点，指向两套完全不同的解法。

**业务痛点必须在核心价值之前。** 没有痛点清单，「哪些买得到」就无从判断，因为买得到与否是相对于具体痛点说的。

**核心价值必须在产品战略之前。** 实施顺序的论证依赖「买不到的那部分是买得到那部分的前提」这个依赖方向，这个方向是上一环的产出。

后三环（整体规划 → 项目树 → 用户故事）的顺序比较松，可以来回走：整体规划的未定项常常要等某个项目试过才定得下来。

## 可信边界

**样本只有一个域。** 七环是从一个真实域提炼的，n = 1。另一个域推进时该回来修这一节。

后两环没有实践检验。 `项目树/` 与 `用户故事/` 至今是空的，那两环的判据是从 [[流程与用例驱动设计]] 推出来的，不是做出来的。

整条链假设你有权改这个系统。 只有只读权限时，后四环没有意义，那种情况该走 [[系统架构拆解]] 单独一套，产出落 `学习/`。

「顺序不能换」是经验不是证明。 上面三条论证说的是换了会怎样，依据是一个域里踩过的坑，不是对照实验。遇到换了顺序反而顺的情况，该修的是这一节。
