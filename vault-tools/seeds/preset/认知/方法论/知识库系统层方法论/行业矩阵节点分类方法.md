行业矩阵节点分类方法，用来描述多个业务平台与工程系统如何共同完成行业链路。先确定行业与机构视角、成员范围和协同问题，再建立关系记录与相应视图。成员内部的对象、规则和实现各有维护处，矩阵重点解释跨边界关系。

## 问题起点

跨平台链路需要同时回答谁负责、谁供数、谁消费以及失败后谁处理。只罗列成员无法说明协同；把各成员完整模型复制到一起，又会产生多份不一致的定义。

## 核心构件

### 成员与范围

| 构件 | 记录什么 | 边界 |
|---|---|---|
| 观察范围 | 行业、机构视角、业务链起终点、当前或目标 | 不把一个机构的分工直接当成全行业事实 |
| 成员表 | 成员标识、一句话职责、引用能力与责任方 | 引入成员不等于展开全部内部设计 |
| 对象口径 | 主数据归属、业务对象、状态与标识的定义来源 | 成员语义差异通过映射表达 |
| 跨边界关系 | 来源、目标、触发、载荷、关联与失败责任 | 只确认有依据的边 |
| 范围缺口 | 未覆盖成员、待确认契约、未知路径与同步状态 | 图形完整不等于关系已确认 |

一个成员可以出现在多个矩阵；每个矩阵明确本次引用的能力范围，成员事实仍在原维护处更新。

### 关系记录

| 字段 | 需要回答 |
|---|---|
| 关系标识与状态 | 如何在不同视图中认出同一关系，是当前、目标还是待确认 |
| 来源与目标 | 谁发起、谁接收；箭头表示依赖、调用还是数据流 |
| 触发与业务结果 | 什么条件触发，跨边界后需要达成什么 |
| 载荷与关联 | 传递什么对象，用什么标识与上下文关联 |
| 权威与责任 | 谁定义数据口径，谁承担交付与消费责任 |
| 失败与恢复 | 超时、重复、乱序或拒绝由谁检测和处理 |
| 依据与时点 | 契约、业务确认或运行证据来自哪里，适用何时或哪个版本 |

字段随问题深度展开。尚未知晓的载荷或恢复方式标记未知，不按技术常识补成既有机制。

### 视图选择

| 读者问题 | 视图 | 组织维度 |
|---|---|---|
| 哪些成员相互依赖 | 关系视图 | 成员与依赖范围 |
| 一笔业务怎样跨边界完成 | 端到端链路 | 角色或系统泳道、阶段与交接 |
| 数据从哪里来、流向哪里 | 数据流 | 权威源、加工路径、单据链与消费方 |
| 各对象经历哪些阶段 | 生命周期 | 选定对象的状态与关键事件 |
| 故障传播和恢复责任是什么 | 关键运行场景 | 失败点、影响范围与补偿责任 |

视图按问题选择，不要求全部建立。不同视图复用成员与关系标识，只改变组织维度和详略。

### 口径一致

一张图只表达一种箭头语义和一个主要抽象层级。需要同时解释调用与数据流时，分图或明确分开图例，避免把“依赖”误读成“供数”。

每个图元能追到成员或关系记录。关系记录再指向契约或业务定义，避免在每张图里重写同一对象的字段与规则。

发生冲突时，先检查是否描述同一范围、时点和状态，再核对证据与责任方。图、成员说明和契约都可能过期，不能规定某种文档天然优先。

## 操作规则

1. 确定要解释的协同问题与范围排除，列出成员、引用能力和业务链起终点。
2. 盘点各成员已确认的对象、主数据归属、契约与运行关系，列出未知项。
3. 为跨边界关系建立记录，区分当前链路、目标设计和待确认假设。
4. 根据读者问题选最少的视图，用相同标识复用成员和关系。
5. 从一笔业务或一条数据抽查链路，检查触发、交接、标识和失败责任是否闭合。
6. 成员或契约发生变化时，沿关系标识检查受影响视图；尚未同步的范围显式标识。

### 最小产出

| 产出 | 完成条件 |
|---|---|
| 成员范围 | 每个成员能说清引用什么、谁负责、哪些内容不展开 |
| 关系清单 | 每条边有明确语义、方向、状态与依据；未知项可见 |
| 跨平台视图 | 能回答选定问题，图元可追到关系记录 |
| 同步规则 | 变更能找到受影响关系与视图，维护责任明确 |

### 验收判据

- 单域字段、规则和状态机没有在矩阵中平行维护。
- 同一关系在多视图中的含义、方向和状态一致。
- 生命周期、数据流和调用关系没有被混成一条无语义的连线。
- 关键交接能说明结果责任；尚未确认的契约和恢复方式没有被画成事实。
- 矩阵引用不改变成员原有的业务边界或工程身份。

## 可信边界

矩阵的完整性受成员知识和契约可见性限制。关系清单和抽样链路能暴露缺口，但不能自证覆盖全部行业业务。

多视图与关系复用是组织方法，不替代业务建模、接口设计和实际联调。建设推进可以针对一条协同链路开展，不要求把所有成员的内部工程全部拆完。
