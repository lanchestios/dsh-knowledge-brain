知识库系统层分层方法，用来区分行业协同、业务范围和工程实体。先确定对象，再判断关系，最后决定命名与组织方式。业务分解、工程组成和系统对业务的支撑是不同关系，不能合并为一条包含链。

## 问题起点

同一个词可能描述业务职责、产品包装或工程实现。名称含“平台”不必然是业务平台；一个系统拥有多个仓库也不必然成为多个系统。分层依据是要解释的对象及其稳定边界。

## 核心构件

### 节点判型

| 对象 | 判型问题 | 主要展开对象 |
|---|---|---|
| 行业矩阵 | 是否解释多个业务范围与工程实体如何协同 | 成员、端到端链路、数据流和跨边界依赖 |
| 业务平台 | 是否描述一组相互关联的业务目标与职责 | 子域、能力、业务接缝及支撑系统 |
| 业务子域 | 是否在既定业务范围中继续分解职责 | 对象、规则、流程、输入输出及责任 |
| 工程系统 | 是否描述承担明确责任、对外提供契约的工程实体 | 模块、功能、运行路径、数据与部署 |
| 模块或构件 | 是否是在某个系统边界内承担局部职责的实现单元 | 内部机制、接口及依赖 |

业务平台可能由一个或多个系统支撑，也可能部分依赖人工流程。系统数是现状信息，不能作为平台身份的必要条件。

### 四类关系

| 关系 | 含义 | 不应推导 |
|---|---|---|
| 业务分解 | 业务范围按职责与规则分为子域 | 每个子域必须对应一个系统 |
| 工程组成 | 系统由模块、服务、库或其他构件组成 | 每个构件都拥有独立系统身份 |
| 支撑映射 | 系统或人工过程实现某域的一项能力 | 系统边界与业务域边界必然重合 |
| 行业协同 | 多个成员通过契约与流程完成跨边界结果 | 成员被协同视图引用后必须改变归属 |

```text
业务视角：业务平台 → 子域 → 能力
                         ↑ 支撑映射（多对多）
工程视角：工程系统 → 模块 / 服务 / 构件

行业协同：引用相关业务范围与工程实体，组织跨边界链路
```

业务与工程各有自己的分解结构，映射负责解释两者怎样对应；协同视图选择需要的成员与关系。

### 边界依据

业务边界优先检查共同目标、术语与规则、对象生命周期、输入输出和责任归属。若相邻范围对同一词有不同含义，应明确各自语义与转换关系，不强求统一成一个模型。

工程边界综合检查稳定职责、暴露与消费的契约、数据责任、变更与运维责任及演进生命周期。独立部署、仓库和团队分工可以提供线索，但单独一项不足以定型。

同一系统参与多个业务范围时，系统事实只维护一次，各业务视角引用其覆盖能力。只知道对外契约的系统也能判型，内部不可见不影响记录它的工程责任。

### 组织归属

目录用于选择主要阅读路径，引用用于表达跨路径关系。一个对象有多个视角，不要求复制多份对象正文；父子目录也不能证明业务上的父子关系。

“子域”取决于本次业务分解的上下文，“子系统”取决于本次工程边界。放到更高层目录不会自动改变对象性质。

### 易混情形

| 情形 | 判断方式 |
|---|---|
| 新增第二个系统 | 重新检查业务范围和系统关系；不自动升格为平台 |
| 新增服务、仓库或部署 | 先检查是否只是既有职责的实现变化 |
| 系统内部使用领域模型 | 可以映射业务域，但模型名称本身不产生新平台 |
| 目标设计拆出新系统 | 标记为目标工程边界，与已运行系统分开 |
| 共同权限或审计机制 | 按覆盖范围建立共享责任，不能随意归给一个业务分支 |

## 操作规则

1. 写清当前问题：行业如何协同、业务如何分工，还是工程实体如何工作。
2. 为对象列一句职责、主要对象或能力、外部接缝和范围排除。
3. 用边界依据检查对象身份，并为每条关系标明是分解、组成、支撑还是协同。
4. 按类型选择 [[行业矩阵节点分类方法]]、[[业务平台节点分类方法]] 或 [[业务系统节点分类方法]]。
5. 再按 [[系统知识内容组织]] 选择主要维护处与读者入口，不以目录位置替代边界判定。
6. 业务目标、契约或责任显著变化时重新判型；保留变更涉及的对象映射，不按数量自动调整层级。

### 判型记录

| 项 | 记录内容 |
|---|---|
| 对象 | 名称、一句话职责、本次观察范围 |
| 依据 | 业务目标、规则、契约或责任中哪些支持当前判型 |
| 下一层 | 准备继续拆的是业务职责还是工程构件 |
| 关联 | 支撑哪些能力，参与哪些协同链路 |
| 状态 | 当前、目标或待确认；未知边界及验证方式 |

### 验收判据

- 每个节点能说明描述的对象与判型依据，名称只作提示。
- 业务与工程没有被写成强制一一对应的层级。
- 同一系统支撑多域、一域由多系统支撑均可表达。
- 系统内部构件与目标系统切片没有被误报为已运行的独立系统。
- 引用、目录归属和事实维护责任各自明确。

## 可信边界

这套分类是知识组织的判断口径，不是系统独立性的形式化公式。复杂集成、共享内核和组织调整可能使边界暂时模糊，应记录争议与证据，不用仓库数、部署数或目录深度替代判断。

按领域、职责与契约选择分支的方式可以帮助减少混层，但无法仅凭知识目录证明业务划分合理；边界仍需由实际目标、责任和运行事实检验。
