系统知识建设推进，用来把对业务与系统的理解转为有依据的建设决策和可验收交付。现状、痛点、价值、战略、规划、项目与故事构成相互依赖的七个环节；按本次目标选择必要环节，允许带着问题往返核验。

## 问题起点

建设容易在两处脱节：从现象直接跳方案，或把目标拆成大量动作却没有可验收结果。推进链要求每个决定都能追到问题与证据，每个交付都能说明服务什么结果。

[[系统知识内容组织]] 处理产物的阅读与维护，这里处理产物之间的输入依赖与完成条件。只读理解可以停在现状与问题；设计建议不等于已经获得建设决策权。

## 核心构件

### 任务入口

| 情形 | 基线 | 本轮终点 |
|---|---|---|
| 只理解现状 | 已有职责、契约、结构与运行证据 | 解释与问题记录，不自动进入建设 |
| 现状改进 | 当前能力、痛点、约束与依赖 | 目标差距与可验收改进 |
| 全新建设 | 业务目标、现行业务过程、约束及可复用依赖 | 从需求与方案形成工程边界和交付 |

### 七个环节

| 环节 | 主要产出 | 完成判据 |
|---|---|---|
| 拆解现状 | 职责、关键路径、现有能力和证据缺口 | 范围内的关键断言可回验，事实与假设分清 |
| 业务痛点 | 流程断点、承担成本者、反馈者及影响 | 现象有证据，原因与推测分别记录 |
| 核心价值 | 受益者、期望结果、衡量方式与差异化 | 说明改善什么、为何值得，以及怎样判断改善 |
| 产品战略 | 优先结果、实现策略、顺序与取舍 | 价值、依赖、成本和风险支持该选择 |
| 整体规划 | 能力边界、依赖、阶段与未定项 | 路径可解释，关键契约与决策缺口可见 |
| 建设项目树 | 围绕结果组织的项目与交付包 | 每项有起点、终点、交付物、责任、依赖和验收 |
| 用户故事 | 场景中的角色目标与验收条件 | 结果可验证，边界清楚，可继续分解实施任务 |

新建系统的现状包括已有业务过程、约束与可复用能力，不要求先有现成工程。微小变更可以简写价值与策略，不为流程齐全制造独立文档。

### 痛点与价值

| 痛点记录 | 价值记录 |
|---|---|
| 断在哪个业务环节，发生于什么条件 | 改善哪个受益者的什么结果 |
| 谁承担成本，谁提出反馈 | 基线、目标、观察周期与衡量方式 |
| 频率、影响与现有替代方式 | 为什么值得做，哪些能力具有差异化 |
| 已知原因、待验证原因与依据 | 预期收益、约束与可能代价 |

承担成本者与反馈者可能不同，不能按声音大小直接排序。先保留原始度量，如处理时长、差错率和交接次数；金额估算需公开计算模型、数据来源、采纳率等假设，并区分实测与预测。

核心价值回答业务结果，建或买回答实现策略。明确价值和约束后，再评估自建、采购、复用或组合；没有采购决策权时，可以说明评估边界，不必跳过价值判断。

### 战略与规划

战略说明优先达成哪些结果、采用什么策略以及放弃什么。顺序同时考虑业务价值、前置能力、成本、风险和学习收益，不能把某一种依赖方向预设为所有建设的答案。

规划不仅画分层图，还要说明依赖方向、契约、迁移过程和阶段验收。未定项记录候选、各自后果、需要的验证与决策责任，避免用一张完整的图掩盖未做的决定。

已有系统的小步改进可以用台账：问题本质、现象与证据、现有替代方式、候选处理、价值与验收。未实现能力与现有问题分开；没有替代方式时如实写无，尚未查清时写未知。

### 项目与任务

建设项目树表示业务目标、项目和交付包之间的分解关系。代码树表示仓库与文件组成，部署树表示运行单元与环境；三者通过映射关联，不共用一个含糊的“项目树”。

| 交付契约 | 需要回答 |
|---|---|
| 目标与范围 | 改善什么结果，本次包括和排除什么 |
| 输入与依赖 | 依赖谁提供什么能力、数据或决策 |
| 输出与接口 | 交付什么，后续工作怎样使用 |
| 完成证据 | 用什么场景、指标、检查或测试验收 |
| 责任与约束 | 谁决定、谁实施，受哪些权限与风险约束 |

任务以独立可验证、可评审的交付为边界；步骤是任务内部具有检查结果的单个动作。环境准备、配置和说明并入它们服务的交付，只有确有独立使用者和验收时才单列。

### 顺序与回路

可以先访谈痛点或收集故事，再带着问题拆解现状；但对原因下结论、确定方案与优先级之前，需要相应证据。价值与约束应能支持策略，规划应能支持项目范围，故事与任务应能追到需求和验收。

试验可能改变规划，故事可能暴露边界缺口，运行反馈可能推翻痛点原因。回到相关环节更新依据，比强行维持一次通过的顺序更可靠。

## 操作规则

1. 确定本轮建设目标、观察范围和决策权限，选择需要完成的环节。
2. 按 [[业务系统节点分类方法]] 或 [[业务平台节点分类方法]] 获取现状，记录观测时间或版本；口述与文档、配置或运行结果交叉核验。
3. 建立痛点与价值记录，分清现象、原因、基线、目标和假设。
4. 比较策略并写明顺序依据，形成可追踪的能力规划和未定项。
5. 按交付结果拆项目；需求覆盖不清时先用 [[流程与用例驱动设计]] 核对端到端流程、参与方与跨系统步骤，再用 [[用户故事写法]] 写场景与验收。跨模块结果保持同一用户语义，不把流程步骤直接当作故事切片。
6. 将故事细化为实施任务，明确输入输出、依赖、验证和交接条件。
7. 进入排期前补齐规模评估、依赖可用性、实施资源、权限和风险；完成后用验收证据更新状态与知识。

### 追踪记录

| 业务结果 | 问题与依据 | 能力或方案 | 项目、故事与任务 | 验收证据 | 状态与阻塞 |
|---|---|---|---|---|---|
| 可衡量结果 | 指回事实与假设 | 对应方案及决策 | 可多对多关联 | 指标、场景或检查 | 未开始、进行、完成或受阻及原因 |

### 验收判据

- 每项建设能够追到问题与价值，技术支撑项也能说明服务哪些结果。
- 项目有完整交付契约，任务与步骤没有被混用，代码或部署组成没有冒充建设分解。
- 故事有验收不等于已经可排期；依赖、规模、资源与风险已单独判断。
- 现状、目标、方案与假设分开，未定项有验证和决策责任。
- 完成状态由交付证据支持，不能只凭文档、代码或任务清单已经存在。

## 可信边界

七环是建设判断框架，不是所有对象必须依次走完的固定流程。只读任务、受托实施和跨机构协同可能具有不同终点；应明确哪些决定在本轮权限之外。

技能中的需求、计划与任务追踪及独立验收边界可以提供组织参考，但不能保证战略正确、估算准确或收益兑现。结果仍需在真实业务与运行环境中验证。
