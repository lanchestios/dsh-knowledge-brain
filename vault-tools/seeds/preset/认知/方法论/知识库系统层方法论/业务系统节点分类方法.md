业务系统节点分类方法，用来描述一个工程实体承担什么职责、由哪些构件组成、怎样运行及与外部交互。先界定系统边界和本次任务，再按证据可见性决定拆解深度。系统可以有多个仓库、服务和部署，也可以同时支撑多个业务域。

## 问题起点

工程系统的知识不能只剩目录清单或技术栈。理解系统需要把构件与运行路径连起来；推进建设还需要分清观察权限、变更权限以及目标与现状的差距。

## 核心构件

### 边界记录

| 项 | 判断内容 |
|---|---|
| 工程职责 | 系统对外承诺什么结果，明确不承担什么 |
| 外部契约 | 谁使用它，暴露或消费哪些接口、事件和数据 |
| 数据责任 | 拥有哪些状态或权威数据，哪些只是引用和缓存 |
| 生命周期 | 哪些部分共同发布、升级、退役或受兼容约束 |
| 变更责任 | 谁能确认语义，谁开发、运维和处理故障 |
| 观察范围 | 本次描述哪个环境、版本或时点，哪些内部不可见 |

独立部署、独立仓库和独立团队是边界线索，不能单独作为系统独立性的公式。规划中的系统边界是设计提案，不据此声称已经存在独立工程实体。

### 可见性与任务

| 可见条件 | 优先完成 | 深度边界 |
|---|---|---|
| 只能看到公开或对接面 | 职责、契约、输入输出、错误和使用约束 | 不补猜内部模型与存储 |
| 可读实现与配置 | 构件、机制、调用和数据路径 | 每项关键断言仍需证据 |
| 可观察运行 | 真实输入、输出、日志与关键失败路径 | 单次运行不能证明全部行为 |
| 可访谈相关人员 | 语义、约束、历史取舍与责任 | 口述解释与运行事实交叉核验 |
| 有建设权限 | 问题、目标、候选方案和交付 | 不把可读权限视为改造授权 |

外购与自建只是常见条件，不能代替实际可见性判断。外购系统也可能有详细文档，自建系统也可能缺少可读实现。

### 拆解视角

| 视角 | 关键问题 | 产出 |
|---|---|---|
| 定位与上下文 | 为什么存在，与谁交互 | 职责、范围、术语、外部关系 |
| 构件与责任 | 由什么组成，各管什么 | 构件清单、契约与依赖方向 |
| 关键运行路径 | 一次请求、事件或数据怎样完成 | 触发、步骤、状态变化、输出与失败责任 |
| 数据与契约 | 谁定义和维护状态，怎样对接 | 模型、标识、接口、事件与一致性边界 |
| 部署与质量 | 在哪里运行，故障怎样传播 | 拓扑、环境差异、性能与安全约束 |
| 取舍与风险 | 为何这样做，哪些尚未确定 | 决策依据、替代方案、后果与未知 |

具体功能、架构、实现和故事的切分按 [[系统层成员拆解方法]]。这些视角对同一对象可以多对多关联，不要求每个构件在每个视角都有一页。

### 证据对账

| 判定 | 含义 | 处理 |
|---|---|---|
| 已确认 | 断言在指定范围和时点有证据支持 | 写明适用边界与回验位置 |
| 有冲突 | 文档、口述、代码或运行表现不一致 | 保留各自范围，核对版本与条件 |
| 未确认 | 尚未取得足够依据 | 标记假设或未知，给出验证方式 |

现状断言至少能够追到文档条款、代码位置、配置、运行记录或业务确认，并记录观测日期或适用版本。活跃开发无需冻结全部工程，但仍需知道结论描述的是何时的状态。

## 操作规则

1. 明确本次是理解现状、说明用法、设计目标还是推进建设，写出任务终点。
2. 按 [[知识库系统层分层方法]] 完成边界记录，列出相邻对象及只引用的能力。
3. 先读已有设计与契约，形成职责和构件地图；再按可见性取得实现、配置、运行与访谈材料。
4. 选取关键正常路径和高影响失败路径，逐条核对跨构件交互与状态变化。
5. 将已确认、冲突与未知分开处理；按 [[系统知识内容组织]] 建立读者入口和事实维护处。
6. 用“改动某项能力会影响什么”抽查理解；需要建设且具备权限时，再进入 [[系统知识建设推进]]。

### 验收判据

- 不看源码也能解释职责、主要构件及至少一条范围内的关键运行路径。
- 外部契约、数据责任、依赖与错误处理能够关联，未把部署或仓库清单当成全部结构。
- 内部不可见的部分仍有明确边界，没有凭经验补造实现。
- 关键现状可回验，冲突与未知可见；目标能力没有混进当前能力。
- 只读理解与实际建设的任务范围明确，系统内部模型没有仅凭名称被升格为业务平台。

## 可信边界

系统边界可能受共享数据、共同发布和历史集成约束影响，无法只靠一张图确定。证据不足时，先描述可确认的职责与契约，不强求拆到内部构件。

关键路径抽查能够检验理解，但不能自证覆盖全部行为。现状会随工程变更而失效，证据时点和后续维护责任同样属于知识质量。
