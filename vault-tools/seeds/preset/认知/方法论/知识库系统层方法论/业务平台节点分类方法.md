业务平台节点分类方法，用来把一组相关业务拆成职责明确的子域，并说明这些业务由哪些系统或人工过程支撑。业务规划按职责与能力展开，现状盘点按真实工程实体展开，两者通过覆盖映射联系。

## 问题起点

部门、厂商模块和仓库结构各自服务于不同目的，不能直接替代业务边界。一个子域可以由多个系统共同支撑，一个系统也可能横跨多个子域；业务平台的身份不取决于系统数量。

## 核心构件

### 四种描述

| 描述 | 主要单位 | 需要回答 |
|---|---|---|
| 业务全景 | 整体业务范围 | 为谁创造什么结果，边界在哪里，怎样与相邻业务交接 |
| 业务规划 | 子域与能力 | 需要哪些职责、规则、流程和开放面 |
| 现状盘点 | 系统及人工过程 | 实际承担什么，哪些可见，覆盖到哪里 |
| 建设规划 | 差距与交付 | 哪些目标尚未满足，怎样形成可验收的建设范围 |

四种描述可以先从一份简明全景起步，有独立问题后再展开。目标中的系统切片与已经存在的系统分别标识。

### 子域边界

| 项 | 记录内容 |
|---|---|
| 目的与结果 | 子域服务的业务目标和可观察结果 |
| 对象与规则 | 负责哪些对象生命周期、状态与不变量 |
| 输入与输出 | 消费什么、产出什么，哪些事件触发交接 |
| 责任归属 | 谁确认业务语义，谁处理例外与争议 |
| 相邻边界 | 哪些能力属于邻域，共用对象怎样引用或转换 |
| 范围排除 | 哪些看似相关的职责本轮不承担，原因是什么 |

边界候选用真实场景检验：同一关键规则若必须在多个子域同时改动，可能是边界不清，也可能需要显式共享机制；先查业务原因，不急于合并或拆分。

### 子域展开

| 内容 | 关注点 |
|---|---|
| 域全景 | 职责、术语、能力清单与相邻接缝 |
| 领域模型 | 对象、关系、字段、枚举、状态与规则 |
| 业务流程 | 主线、例外、时序、周期节拍与责任交接 |
| 开放面 | 接口、事件、标识及消费方承诺 |
| 产品分工 | 面向用户的能力组合与交互边界 |

展开的深度由问题和证据决定，不要求每域长出同样的子页。权限、审计或共同数据口径跨多个子域时，由覆盖它们的共同层维护规则，域内只记录特有约束与引用。

### 现状可见性

| 条件 | 优先记录 | 限制 |
|---|---|---|
| 内部不可见 | 工程职责、对外契约、权威源、入口出口与运行边界 | 不猜内部表、模块与算法 |
| 内部可读 | 主要构件、调用与数据机制、证据位置 | 可读不代表可决定改造 |
| 包含人工过程 | 角色、输入输出、处理规则、控制点与成本 | 不把人工环节伪装成系统能力 |
| 有建设权限 | 目标差距、候选交付、依赖与验收 | 决策权限和实施能力仍需确认 |

### 覆盖映射

| 业务子域 | 目标能力 | 支撑系统或过程 | 覆盖状态 | 证据与缺口 | 责任方 |
|---|---|---|---|---|---|
| 按职责填写 | 可检验的能力 | 可列多个实体，必要时分行 | 已覆盖、部分、未覆盖、未知 | 当前依据、观测时点及未满足条件 | 语义与交付责任 |

已覆盖需有可核验依据；未知表示尚未确认，不能直接算作未覆盖。系统清单和域清单本身不构成覆盖证明。

## 操作规则

1. 建立业务全景，明确目标、主要参与者、相邻业务及范围排除。
2. 按对象生命周期、关键规则与责任形成子域候选，用端到端场景检查交接与遗漏。
3. 对每个子域写出边界记录，再按独立问题展开模型、流程、开放面和产品分工。
4. 独立盘点实际系统与人工过程，记录职责、可见性和现状证据；工程拆解按 [[业务系统节点分类方法]]。
5. 建立域、能力与系统覆盖映射，分清已知差距、未知覆盖和目标设计。
6. 将需要改变的差距交给 [[系统知识建设推进]]，项目围绕业务结果与交付边界组织，故事归属对应业务目标。

### 验收判据

- 子域能说明目标、对象、关键规则、责任与相邻接缝，未照搬部门或厂商分类。
- 规划能力与现状系统可分别阅读，并通过覆盖映射相互追踪。
- 一系统多域、一域多系统和人工环节都能表达，未知不被当成缺失事实。
- 共用规则没有任意归入单一分支；域内特例与共同规则分清。
- 建设项目有业务结果与验收范围，代码仓库或部署树没有被当作项目树。

## 可信边界

业务域没有通用的最优数量。边界会受到行业规则、责任分工与历史约束影响；不同机构可以对同类业务采用不同分解。

覆盖映射是差距判断的依据，不自动给出建设顺序。先解决哪一项仍需结合价值、依赖、成本和风险决定；未知覆盖需要调查，不能仅凭目录缺页发起建设。
