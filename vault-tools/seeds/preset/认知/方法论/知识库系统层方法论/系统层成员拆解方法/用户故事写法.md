用户故事写法，用来把角色在特定场景中要达成的结果写成可讨论、可验证的需求。故事以角色、场景、目标和价值为主线，配合业务规则、范围与验收条件；角色分类可以用作阅读索引，不能直接当成故事切片。

流程与跨系统参与方尚未厘清时，先用 [[流程与用例驱动设计]] 检查覆盖，再按本页的结果与验收判据切故事；一条流程可以对应多条故事，一条步骤也可能只是故事内的动作。

## 问题起点

“某角色需要哪些功能”可以形成需求全景，却通常太大，无法直接验收。反过来，按前端、后端和数据库拆成三条“故事”，又会失去用户结果，只剩技术动作。

## 核心构件

### 故事记录

| 项 | 需要说明 |
|---|---|
| 角色与场景 | 谁在什么情境中遇到问题，不以组织职位机械代替角色 |
| 目标与价值 | 想完成什么，为什么需要这个结果 |
| 范围与前置 | 对象、权限、状态、输入和本次排除项 |
| 主要过程 | 参与者动作、系统行为及可观察反馈 |
| 规则与例外 | 共同规则引用、特殊条件、边界和高影响异常 |
| 验收条件 | 怎样判断结果成立，以及失败情形应怎样表现 |
| 关联与状态 | 对应目标、功能、方案和任务；待实现、部分、已验收或其他明确状态 |

可以用“作为某角色，在某场景下，我希望完成某目标，以获得某价值”起句，但一句格式正确的话并不等于需求已清楚。

### 验收条件

验收描述可观察行为与结果，避免“体验良好”“支持相关功能”等无法判断完成的句子。正常路径之外，选择影响结果或风险的边界条件，不追求穷举所有技术输入。

| 写法 | 必须清楚的内容 |
|---|---|
| 检查清单 | 输入或前置、动作、预期结果和必要约束 |
| Given / When / Then | 已知什么条件，发生什么动作，应观察到什么 |
| 场景表 | 不同条件对应的行为、结果和异常反馈 |

非功能要求在适用场景下写成可验证约束，如响应时间、数据可见性或审计要求。不要脱离实际依据编造阈值；尚未决定的阈值保留待决状态。

### 纵向结果切片

纵向切片让每条故事仍能完成一个小而完整的用户结果，即使底层需要多个技术模块协作。拆分可以收窄场景、业务规则、对象范围或输入变体，但不能去掉让结果成立的必要环节。

| 过大或错误切法 | 改进方向 |
|---|---|
| 一个角色的全部需求 | 按该角色的不同场景与目标分组，再拆可验收结果 |
| 先前端、再后端、再数据表 | 保留用户结果为故事，技术层工作作为实施任务 |
| 一条覆盖所有规则和对象 | 先选一种明确规则与对象范围，后续切片各自保留完成条件 |
| “处理异常”单独作为空泛故事 | 明确哪种失败、谁恢复、恢复后得到什么结果 |
| 只剩准备或配置动作 | 并入服务的交付；若有独立使用者与结果，再单列任务或故事 |

拆分前后核对总范围，避免为追求小而遗漏关键规则。确实不能独立验证的几个步骤留在同一条故事或交付内。

### 技术支撑与实施任务

技术使能项可以独立立项或验收，如迁移、共享基础能力和可观测机制；需要说明服务哪些业务结果、提供什么契约以及怎样验证，不必伪装成某个虚构用户的故事。

故事说明用户语义，实施任务说明怎样交付。一个故事可以对应多个技术任务，一个公共技术任务也可以支撑多个故事，通过追踪关系保留依赖和验收边界。

### 故事与现状

故事所在位置不决定实现状态。现状功能能支持到哪里，由运行与实现证据确认；用户目标是否合理，由业务语义与约束判断。二者冲突时先澄清是否描述同一场景和时点，再分别确认目标、事实与差距。

不能因为当前实现做不到就静默降低用户目标，也不能因为需求写了就宣称当前已支持。裁定记录说明改需求、改实现还是保留差距，以及相应依据。

### 挂法随节点

故事页建在对应的系统或域内部：已建系统放它的落地抽屉内，规划中的域放规划抽屉内，不铺在门面层——挂哪随该节点当前是已建还是规划中走，不另立故事专区。

### 角色导航

角色来自目标、责任和使用情境，同一个人可以承担多个角色。按角色、流程或功能建立阅读索引时，引用同一条故事，避免产生多份略有差异的需求。

故事数量多时先按目标或业务过程聚类，再下钻具体场景。故事本身有稳定标识和范围，改名或重组后仍能追到目标与验收。

## 操作规则

1. 从业务目标和真实场景识别角色，列出需要的结果及价值。
2. 按故事记录补齐范围、前置、主线、规则与验收，区分事实、目标和待决项。
3. 用纵向结果切片收窄过大需求，逐条检查是否仍有可观察的完整结果。
4. 将技术支撑项和实施任务单独识别，写清输入输出、依赖与验证，不强行套用户故事句式。
5. 关联目标、功能、架构、实现与任务，检查每个需求有验收、每项任务有服务对象。
6. 进入 [[系统知识建设推进]] 的排期判断前，再评估规模、依赖、资源、权限与风险；故事文档不代替排期表。

### 验收判据

- 每条故事能说明谁在什么场景中需要什么结果与价值。
- 主线、边界和适用异常可以判断完成，质量约束和待决项清楚。
- 跨多个技术模块仍以用户结果验收，前后端步骤没有冒充独立故事。
- 技术使能项有真实交付契约，不虚构用户价值；故事和实施任务相互追踪。
- 角色索引没有复制故事，当前实现与目标需求的差距没有被静默抹平。

## 可信边界

角色、目标、主线、边界与验收结构参考了公开需求和计划技能；“纵向结果切片”是依据独立验收边界作的方法归纳，不是所比较技能的逐字规则。

用户故事适合表达场景价值，不能承载所有工程工作。迁移、研究、安全修复和平台使能可能更适合交付任务或决策记录；有清晰验收也不等于规模已知或可以立即排期。
