系统架构拆法，用来解释系统的重要边界、构件协作和质量取舍。按需要回答的架构问题选择视图，既可以描述结构，也可以描述关键运行行为、数据责任和部署约束；具体执行细节通过实现记录关联。

## 问题起点

只有静态构件图，难以解释一次请求如何完成及故障如何传播；把所有技术细节都写入架构说明，又会失去层级。架构关注的是影响多处设计或关键质量的结构与机制，而非某种固定图型。本页管自己负责的系统在系统层架构成员内部怎么选视图与切页；拆别人造的外部系统走另一套逆向流程，见 [[系统架构拆解]]，别混用。

## 核心构件

### 关切选择

| 关切 | 需要回答 | 常用表达 |
|---|---|---|
| 上下文与边界 | 谁与系统交互，责任怎样划分 | 上下文图、职责与契约表 |
| 构件与依赖 | 由哪些部分组成，谁依赖谁 | 构件图、依赖与接口表 |
| 关键运行行为 | 核心请求、事件和失败场景怎样跨构件完成 | 时序、状态机或场景图 |
| 数据与一致性 | 谁拥有状态，跨边界如何保证一致 | 数据归属、关系图与一致性说明 |
| 部署与故障域 | 运行在哪里，怎样隔离、扩展与恢复 | 部署拓扑和故障影响分析 |
| 横切机制 | 权限、事务、审计、错误处理怎样贯穿 | 公共机制与适用边界 |
| 决策与质量 | 为什么这样设计，满足哪些约束 | 质量场景、候选比较与决策记录 |

视图按问题和证据选择，不要求每项独立成页或每个系统具备同样的关切集合。

### 构件记录

| 项 | 记录内容 |
|---|---|
| 职责与范围 | 构件解决什么问题，排除哪些职责 |
| 暴露与消费 | 提供和依赖哪些契约，输入输出语义是什么 |
| 状态与规则 | 拥有哪些状态，维护哪些关键约束 |
| 交互与失败 | 正常路径怎样协作，失败怎样影响其他构件 |
| 变化与扩展 | 扩展点、兼容约束和可能变化的边界 |
| 证据与状态 | 当前依据、目标设计或待确认假设 |

外部内核和服务依赖重点说明采用范围、适配责任、升级与失败边界。只有形成独立架构问题时再单独展开，不要求每个外部依赖拥有一页。

### 抽象层级

一张图保持一致的主要抽象层级，箭头语义明确。构件级依赖图不随意混入某个函数步骤；需要放大时另建局部视图，并指出它对应哪一构件或路径。

每张图先写清问题，再说明能从图中得到什么结论。图没有证据支持的边不要画成确定事实，目标与现状不能用同一种标识混写。

### 架构与实现

架构说明哪些运行机制影响边界和质量，实现说明该机制的具体步骤、代码和存储证据。关键调用链可以是架构场景，逐函数调用和字段写入通常属于实现；判断依据是当前问题和抽象层级，不是有没有技术标识。

部署架构解释拓扑、隔离、扩展和故障传播，部署指南说明实际发布、检查与回滚动作。两者可以描述同一对象，但分别回答原因与执行问题。

### 决策记录

| 项 | 需要说明 |
|---|---|
| 问题与约束 | 什么条件迫使当前设计作出选择 |
| 候选 | 哪些方案确实被考虑，依据是什么 |
| 决定与理由 | 选择什么，理由来自实测、可检验论证还是判断 |
| 后果 | 带来什么收益、成本与限制 |
| 状态 | 当前决定、目标提案或待决，何种条件需要重审 |

未取得当时依据时，记录观察到的结构和推测边界，不把事后解释写成原始决策。

### 目标与追踪

目标架构沿用可比较的问题与质量口径，写清相对现状改变什么、为何改变、怎样迁移和验证。新构件可以没有现状对应，退役构件需说明替代与兼容。

功能、故事、架构和实现按 [[系统层成员拆解方法]] 建立映射。一个共享构件可以服务多项功能，一条故事可以依赖多个构件，不要求三套页面同名成对。

## 操作规则

1. 确定需要解释的边界、关键行为或质量问题，明确当前还是目标。
2. 取得契约、代码、配置、运行或决策证据，识别实际构件与责任。
3. 选择最少且足够的视图，先保持上下文和抽象层级清楚，再按独立问题放大。
4. 为关键构件补齐职责、状态、接口及失败影响，识别共同机制和扩展点。
5. 为重要取舍建立决策记录，区分观察、作者说明和当前判断。
6. 关联功能与实现证据，用一条关键路径和一个变更影响问题检查视图是否能共同解释系统。

### 验收判据

- 每个视图有明确问题、范围、层级和箭头语义。
- 构件职责与契约明确，关键行为、数据责任及适用质量约束能够关联。
- 部署与横切机制按需要出现，具体运维步骤和实现证据各有位置。
- 当前事实、目标设计与推测分清，取舍理由的依据和限制可见。
- 能解释范围内某项变化会影响哪些责任与路径，未以图数量代替理解。

## 可信边界

架构视图是对系统的选择性表达，不是全部实现的镜像。事件驱动、插件式或运行期动态组合的系统，可能需要先按事件、扩展点与状态责任建立视图，再寻找稳定构件边界。

公开技能提供了多视图、接口和决策的组织参考，不证明某种架构风格普遍更优。未取得运行与历史证据时，对性能、故障或设计动机的结论应保留相应限制。
