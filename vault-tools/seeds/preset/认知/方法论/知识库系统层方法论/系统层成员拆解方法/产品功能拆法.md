产品功能拆法，用来把面向使用者的能力拆成清楚、可查的功能主题。功能描述角色能完成什么、怎样触发以及如何判断结果；当前功能与目标功能使用可比较的语义，分别记录真实行为和建设差距。

需要先识别业务流程与参与方时，用 [[流程与用例驱动设计]] 梳理需求覆盖，再回到本页按能力组织功能；用例层次不直接决定功能目录。

## 问题起点

菜单、技术模块和用户目标并不总是一致。同一个目标可能经过多个入口，一个入口也可能承载不同任务。按菜单复制知识容易遗漏规则和例外，按工程模块拆又可能打断使用路径。

## 核心构件

### 功能族边界

| 判断维度 | 观察什么 |
|---|---|
| 共同目标 | 是否服务同一类可观察结果 |
| 对象与规则 | 是否围绕相近对象生命周期和业务约束 |
| 使用情境 | 角色在什么情况下需要这些能力 |
| 责任与变化 | 是否由相近责任维护，是否经常共同变化 |
| 外部接缝 | 与其他能力在哪里交接，交接结果是什么 |

先形成能力全景，再按稳定目标分组。功能族可以与技术模块不同；一个功能需要多个模块支持时，功能主线仍保持完整。

### 功能记录

| 项 | 需要说明 |
|---|---|
| 角色与目标 | 谁在什么场景下要完成什么，获得什么结果 |
| 范围 | 处理哪些对象和情形，明确不包含什么 |
| 前置与触发 | 权限、状态、输入及进入条件 |
| 动作与反馈 | 使用者做什么，系统发生什么可观察动作，返回什么 |
| 业务规则 | 哪些条件约束行为，公共规则引用到哪里 |
| 异常与恢复 | 无权限、无数据、重复、失败等适用情形怎样反馈与处理 |
| 完成证据 | 用什么状态、产物或反馈判断成功 |
| 现状依据 | 适用范围、版本或观测时点，证据及未知项 |

记录深度随功能复杂度调整，不能为了填表补造系统没有的错误处理或恢复机制。

### 操作与实现

操作主线保留完成任务必需的信息，如入口、填写项、协议动作和反馈。内部路由、类、表和调用机制通过 [[系统实现拆法]] 关联；如果对接者确实通过接口完成任务，接口用法属于该任务所需内容。

功能解释可观察承诺，实现解释承诺如何被执行。不能根据页面按钮存在就认定后端行为完整，也不能根据代码中有接口就认定使用者可以完成目标。

### 共同规则

跨多个功能族的权限、入口、导入导出或审计，先检查是否具有共同语义。确有共同规则时由公共层维护；各功能记录适用条件和特例，避免每页复制规则全文。

同名操作在不同场景下语义不同时分别说明，不为减少页面而强行共用。能独立完成任务的操作指南可以按角色建立入口，底层条件和影响仍引用同一维护处。

### 目标与现状

| 规划情形 | 描述方式 |
|---|---|
| 新增能力 | 目标角色、问题、可观察结果与验收；现状覆盖标记为未覆盖或未知 |
| 能力改进 | 当前行为、具体差距、目标条件与约束 |
| 功能合并或拆分 | 旧能力到新能力的对应，用户迁移和兼容影响 |
| 能力退役 | 使用者、替代方案与退出条件 |

目标记录不复制一套尚不存在的操作教程。已有操作不能按未来设计改写；当前确实缺少且影响理解的能力可以说明，愿望清单归目标与差距。

## 操作规则

1. 列出主要角色、场景与目标，形成能力清单，不以菜单或模块名直接定族。
2. 用功能族边界分组，明确每族职责、对象和相邻交接。
3. 选择代表性正常路径及高影响例外，按功能记录描述行为。
4. 识别跨族规则，确定公共维护处；仅有局部语义的能力留在对应功能。
5. 按独立任务与维护需要决定是否继续拆页，完整使用路径不要切成难以复原的步骤碎片。
6. 关联故事、架构与实现，目标能力写差距与验收，当前能力保留证据。

### 验收判据

- 每个功能族能说明服务什么目标，边界依据不只是菜单位置。
- 使用者知道何时能做、怎样做、会得到什么以及怎样判断完成。
- 适用的异常和恢复边界可见，未知机制没有被常识补齐。
- 共享条件与影响只有一处主要定义，场景特例仍可查。
- 当前与目标可比较，跨多个技术模块的功能仍有完整用户语义。

## 可信边界

功能族依赖实际能力与用户任务，不存在通用的族数或命名集合。菜单、角色和模块可以作为线索，但都不能单独证明功能边界。

功能记录借用需求文档中目标、范围与验收的结构。目标文档只说明要实现什么；描述现状时仍需运行、契约或实现证据，不能把期望行为当作事实。
