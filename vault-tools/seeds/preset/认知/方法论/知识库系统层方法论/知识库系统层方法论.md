知识库系统层方法论，是组织行业协同、业务平台和工程系统知识的一套方法。先判断描述对象与本次任务，再划定边界、拆解内容、核对证据，并将目标转成可验收的建设结果。它同时服务于理解现状、说明用法、设计目标和推进建设。

具体系统与平台是方法的应用对象。通用判据由方法层维护；应用中的事实、局部约束和设计决定由相应对象维护。应用发现反例时，应说明失效条件并修订通用判据，不能靠某个应用的目录或门面反过来裁定整套方法。

## 问题起点

业务范围、工程边界、读者问题和建设阶段是不同维度。将它们混成一棵目录树，容易把目标当现状、把服务当系统、把角色当需求切片，或者用大量重复页面制造完整的假象。

这套方法将“描述什么”“怎样拆”“如何组织”“怎样推进”分别处理；共同要求是边界可说明、事实可回验、关系可追踪、结果可验收。

## 核心构件

### 对象与任务

对象决定描述边界，任务决定本轮产出。两者组合选择方法，不因对象相同就强迫执行同一套流程。

| 本次任务 | 需要完成 | 停止条件 |
|---|---|---|
| 理解现状 | 明确职责、结构、关键行为和证据缺口 | 能回答范围内的运行与影响问题 |
| 说明用法 | 明确角色目标、前置条件、操作与反馈 | 使用者可以完成任务并判断结果 |
| 设计目标 | 明确目标、约束、候选方案与验收 | 决策者能理解取舍和未定项 |
| 推进建设 | 将差距转为项目和可验收交付 | 实施者有明确输入、依赖和完成条件 |

### 组织与推进

内容组织处理“在哪里找到、给谁读”，建设推进处理“做什么、依赖什么、何时算完成”。组织完善不代表建设已经完成；完成一个交付也不要求所有知识类别都独立成页。

行业矩阵优先组织关系，业务平台优先组织业务范围，工程系统优先组织职责与机制。读者入口可以不同，底层事实与契约保持同一份定义。

### 共同底线

- 现状、目标、推测分别标识；未核实不等于没有，计划支持不等于已经支持。
- 一项事实有明确维护处；跨视角通过引用与映射关联，避免平行维护同一规则。
- 每层选择一个主要分解维度；覆盖多个分支的规则由共同层维护。
- 目录、命名和模板可以适配，不能代替业务边界、工程责任与证据判断。
- 知识页按独立问题拆，建设任务按独立交付拆；两者不要求一一对应。

## 操作规则

1. 写明对象、读者、本轮问题、范围排除和任务终点，选择适用方法。
2. 先建立最小全景：对象职责、主要构成、关键关系和必要术语，再下钻到独立问题。
3. 清点证据，对关键断言记录来源、观测时间或版本；冲突和未知显式保留。
4. 按读者问题组织入口，用引用贯通不同视角；需要独立维护时再拆页。
5. 涉及建设时，对照目标与现状，补齐价值、依赖、交付与验收关系；只读任务停在理解与建议。
6. 用实际问题抽查产出：能否找到正确规则、解释一条关键路径、判断变更影响，或独立验收一项结果。

### 最小记录

| 项 | 必须能回答 |
|---|---|
| 对象与边界 | 描述什么，哪些相邻对象只被引用 |
| 本轮任务 | 为谁解决什么问题，做到哪里停止 |
| 事实依据 | 哪些已确认，何时观察，哪些仍未知 |
| 关系追踪 | 业务、工程、需求、交付如何相互对应 |
| 完成条件 | 用什么证据判断理解或交付已经成立 |

### 验收判据

- 只读方法即可执行判型和拆解，无需先阅读某个具体系统。
- 业务分解、工程组成、支撑映射和协同关系各有含义。
- 规则、证据与建设目标分清，拆页有独立问题，交付有独立验收。
- 来源方法的适用条件可见，未把技术栈、页数或任务时长变成通用要求。

## 可信边界

这是一套可复用的组织与判断方法，不是软件行业统一分类，也不规定最优域数、页数或目录深度。Skills 对照提供了可迁移的组织方案；将其用于系统知识，是结合任务特征的改编，尚不构成跨行业实效或量化提升的证明。

通用方法不能覆盖所有机构和工程约束。事实出现反例时，应重新检查边界与判据；局部适配应说明原因，不能为了符合模板而改写现状。
