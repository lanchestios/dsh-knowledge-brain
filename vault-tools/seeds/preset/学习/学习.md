我拆过、练过什么。某个具体系统是怎么造的、怎么用的：断言绑定一个具体版本，上游一改就可能不对。学法有两种，读源码拆它怎么造，调 API 写 demo 练它怎么用；学一个框架通常两种都要，先练后拆。

本页是这个区的读写规则，与 `wiki-write` 技能的 `writing.md` 叠加；两边冲突以本页为准。

## 怎么读

回答「某个外部系统在某个版本上怎么造、怎么用」。

- 先找到 `学习/<System>/`，读它的门面页，记下基线：被拆或被练的版本（钉在 `.wiki/anchors.conf`），交回时片段旁注明版本。
- 往下按缩放层级读：层级越深越是单块内部，问整体结构停在上层，问某一块怎么实现再往下。
- 概念不写在这里：页里的双链指向 `知识/` 的概念页，问到概念本身顺着双链去 `知识/` 读。
- 本区额外要带：基线版本。

交回照 `wiki-read` 技能的上下文包：逐字摘原文、出处写到节标题、缺的进「没找到」。

## 什么该进这个区

判据只有一条，`wiki` 技能里已经立好：**要不要钉一份基线才敢写。**

两种学法断言的东西不同，但都绑版本：

| 学法 | 断言 | 基线钉什么 | 骨架 |
|---|---|---|---|
| 拆源码 | 这个系统**在这个 commit 上**是这么造的 | 上游仓的 commit | 研习变体 |
| 练用法 | 这个系统**在这个版本上**是这么用的，调这个 API 跑出来是这个结果 | 自己的 demo 仓的 commit，加上被练系统的版本号 | 练习变体 |

说的是书、方法与判据、不绑版本的，进 `知识/`。

**和 `知识/` 搭配，不重复。** 概念（Loss、Gradient Descent、Overfitting……）只写在 `知识/`；学习页写「这段源码 / 这个 demo 落实的是哪个概念」，用 `[[双链]]` 指过去。练的过程中对概念有了新理解，改的是那一页知识，学习页只留链接。

> Pi 和 Palantir Ontology 都是具体的外部产品，但前者在 `学习/`、后者在 `知识/`——切的是「会不会随上游过期」，不是「项目还是领域」。

## 目录形状：层级 = 缩放倍数

这个区下**不设固定子目录**，形状由被研习的系统决定。但形状自由不等于随便切。层级对应的是放大倍数，不是分类：

```
学习/
└─ <System>/
   ├─ <System>.md          L0–L2  是什么 / 跟外界谁说话 / 由哪几块组成 / 谁依赖谁
   ├─ <构件 A>.md          L3     A 放大之后自己是什么
   ├─ <构件 B>.md          L3
   └─ <机制>.md            L3     横贯多块的一套机制（扩展模型、权限、会话）
```

> **切子页的唯一理由是「这一块放大之后，它自己又是一个系统」。不是「这一块内容多」。**

只有一层的系统就一页，别为了对称造空壳——`系统/` 那边空了很久的 `项目树` 与 `用户故事` 是前车之鉴。

一级目录（系统名）用英文原词，二级及以下中文，专有名词除外。长出子页走 `wiki page grow`，不要手动 `mv`。

练用法的目录按用法主题切章，一章一页，不按 demo 脚本切：

```
学习/
└─ <System>/
   ├─ <System>.md          定义、环境与基线、章节导览、核心构件
   ├─ <章 A>.md            一个用法主题（训练循环、数据加载、设备……），可对应 demo 仓的几个脚本
   └─ <章 B>.md
```

同一个系统先练后拆时，拆源码的子页和练习章并列在同一目录下，index 页两边都导。demo 仓放 `raw/project/<system>-learn`（如 `raw/project/pytorch-learn`），带自己的 git 和虚拟环境；raw/ 不入库，数据集别放进 wiki。关键代码和思考沉淀进章页，仓里只留能跑的东西。

## 页骨架

拆源码用研习变体，练用法用练习变体。

下面先讲研习变体，它是 `知识/知识.md` 的 `系统 / 架构类` 骨架的**研习变体**：保持原有节序，插两节，并按缩放层级拆到两类页上。

### index 页（L0–L2）

```
定义
→ 专有名词（★ 按依赖序）
→ 概念信息流（★ L1 图：跟外界谁说话 + 分成哪几部分，纯概念）
→ 来历
→ 与同类的区别（★ 对照表）
→ 逐部分拆解（长出子页时这里只留每块一句话 + [[链接]]）
→ 构件清单（★ L2：树 + 全构件表 + 依赖图）
→ 关键路径（★ 新增：时序图，1–3 条）
→ 跨构件机制
→ 取舍账（★ 新增：表）
→ 可信边界
```

原有八节的写法、以及「构件清单为什么排在拆解之后」，见 `知识/知识.md`。新增的两节：

**`关键路径`**——`概念信息流` 是纯概念的静态图，这一节是带真实构件名的动态图，两者不重复。挑 1–3 条最重要的执行链：入口 → 调用链 → 副作用 → 出口，用 `sequenceDiagram`。

排在 `构件清单` 之后，因为时序图上全是构件名，读者得先在清单里见过它们。

> 判据：能不能指着图说出「哪一步失败了会怎样」。说不出，说明只抄了调用顺序。
>
> 没有这一节的研习页是半成品。目录树和依赖图画得再漂亮，一问「用户敲一条命令之后发生了什么」答不出，就是只拆了形状没拆行为。

**`取舍账`**——一行一个岔路口：

| 岔路口 | 它选了什么 | 放弃了什么 | 作者给的理由 | 理由硬不硬 |
|---|---|---|---|---|

前四列是观察，最后一列是我的判断，绝不揉进同一句话。硬度三档：给了实测或数据 / 给了可检验的论证 / 只是断言。

排在 `可信边界` 之前：取舍账记作者选了什么，可信边界记这东西的限度，两件事。它替掉了 arc42 的质量目标与 Quality Requirements（质量需求）两节——拆别人的系统时那两节没有主人。

作者当时的约束（时间、团队、既有代码）你看不到。最后一列宁可空着也别编。

### 子页（L3）

```
定位（一句话 + 指回父页）
→ 专有名词（本页新增的，仍按依赖序）
→ 内部构成（★ L3 图）
→ 逐部分拆解
→ 关键路径（本块自己的，可省）
→ 可信边界
```

子页通常没有独立来历，指回父页即可，不留空节。

**`逐部分拆解` 的小节按主题切，不按对账判定切。** 不许出现「新增的一处确认」「两样查无此事的东西」「本次对账推翻最狠的一处」这类小节名——那是拿「我这次查到了什么」当骨架。三类判定的归处是固定的：convergence 与 divergence 融进它本来该在的那一节，absence 进 `可信边界` 且写成「这东西没有 X」而不是「我原来猜有 X」。判断办法是把小节名遮住只看内容，立不住就说明那节的存在理由是过程、不是主题。

**拆一个以被扩展为卖点的部件时，`逐部分拆解` 至少要有这三节**（对应拆源码方法的第四种视角）：

| 节 | 回答什么 | 材料 |
|---|---|---|
| 对外契约 | 别人从哪里接上来、接上来拿得到什么、生命周期归谁管 | 接口定义与类型文件 |
| 可插拔怎么实现 | 加载、注册、冲突裁决、卸载 | 加载器与注册表的源码 |
| 用法谱系 | 已经接出了哪几类东西，**一张表** | 仓库里的真实实例集合，逐个按「挂在哪个点、改变了什么」聚类 |

用法谱系那节最容易被跳过，因为它要求把几十个实例真扫一遍。跳过的代价是：**没人知道这机制到底有多大表达力**，接口上声明的方法有多少是死的也看不出来。

### 练习变体

练用法的 index 页：

```
定义 → 环境与基线（被练系统版本、设备、demo 仓）→ 章节导览（★ 表：章 / 练什么 / 对应哪些知识页）→ 核心构件（★ 这个系统给用法的主要构件、怎么配合）→ 可信边界
```

章页：

```
定位（一句话：这章练什么 + 指回父页）
→ 专有名词（本章新出现的 API 与概念，按依赖序）
→ 对应的知识（★ 表：demo / 落实哪个概念 / [[知识页]]）
→ 关键代码（★ 摘自 demo 仓的代码块，只摘说明问题的那几行，标出脚本路径）
→ 实跑结果（★ 原样贴输出，注明版本与设备）
→ 改参数看现象（★ 表：改了什么 / 看到什么 / 说明什么）
→ 我的理解
→ 常见坑
→ 可信边界
```

几条写法：

- **实跑结果只贴真跑出来的。** 预期的输出、从文档抄的输出都不算，跑不了就标「未实跑」。换了版本或设备结果变了，重跑再更新。
- **改参数看现象是这类页的重心。** 只贴一份能跑的代码，读者学到的是抄；改一个参数、看它怎么坏，才学到这个参数管什么。
- **`我的理解` 和前面的观察分开。** 前几节写跑出了什么，这一节写我怎么想：原来以为是什么、跑完怎么看、还有什么没想通。跨系统都成立的判断，移去 `认知/见解/`，这里留链接。
- **概念不在章页里展开。** 讲到 Loss、梯度下降，写一句它在这段代码里落在哪一行，然后 `[[链接]]` 到 `知识/`。练出了对概念的新理解，改那一页知识。

## 配图约定

图型按信息类型选，完整对照表在拆源码的方法页里。执行层面四条约定加一条硬规则：

- **一张图里箭头只许一种语义。** 依赖图箭头指向被依赖方，数据流图箭头指向数据去处。两种混在一张图里 = 拆成两张。
- 灰底 = 不属于本系统 / 不在本流程里。用 `classDef`。
- 虚线 = 可选，或横贯全流。
- 节点两行：第一行名词，第二行一句职责。

> **一图一句——每张图后面必须跟一句「从这图上该读出什么」。**
>
> 范例：一张包依赖图后跟「主干是一条直线，没有一条反向边，所以底层两个包都能被单独当库用」。读不出这句话，说明画的是「有哪些框」而不是「这些框告诉了你什么」。

一张图只许有一个缩放倍数。L2 的方框旁边挂一个 L3 的函数名，读者就不知道自己站在哪一层。发现混了就拆两张。

### 两个坑

别用 mermaid 的 C4 语法（`C4Context` / `C4Container` / `C4Component`）。它在 mermaid 里仍是实验特性，GitHub 的内置渲染器不支持，在仓库预览和 PR 里直接渲染失败。只借 C4 Model（C4 模型）的分层纪律，图用普通 `flowchart` 画。

C4 的 Code（代码）层类图一律不画。类名随上游重构就变，图当天过期。要讲清一个类型的形状，用表列字段。

其余规则（图里是纯文本就改写成代码块或表、关系图一律 mermaid 不贴图、图片只留 UI 截图与照片）见 `wiki` 技能，这个区同样适用。

## 验收清单

一条不过就别 `wiki page mark … stable`。下面这份管拆源码；练用法的见后面「练习变体另查」。

- [ ] `.wiki/anchors.conf` 里有这个系统的段落，commit 是钉死的 sha
- [ ] `wiki page anchor 学习/<System>` **通过**——查不到的标识符就是 absence（缺失），即编造
- [ ] 通读全页，每个专有名词的首次使用都在它被定义之后
- [ ] 每张图只有一个缩放倍数，且后面跟着一句「该读出什么」
- [ ] 有 `关键路径` 那一节，不是只有静态结构
- [ ] `逐部分拆解` 的小节名遮住之后内容仍立得住——没有一节的存在理由是「这次对账查到了什么」
- [ ] 拆的是可扩展部件时，对外契约、可插拔实现、用法谱系三节齐全，且用法谱系是从真实实例归纳出来的表
- [ ] 取舍账最后一列是判断，没和前四列的观察揉进同一句
- [ ] 正文不带素材的定位信息（章节号、页码、阅读进度），来源只由 `source` 承担
- [ ] 英文原词当主词、括号标中文，每小节首次出现标一次
- [ ] 不看源码，能回答「改 X 会影响什么」
- [ ] `wiki check` 通过
- [ ] `wiki page mark 学习/<System>/<System>.md stable`

还有一条不能机械检查的：**一轮对账下来全是 convergence（吻合），通常不是拆得好，是猜得太保守。** 猜对的部分只确认了已有的理解，猜错的地方才是这个系统真正特别的地方。
