[[OKF开放知识格式]] 和这个仓库长得很像，但前提相反。搞清楚哪些能借、哪些借了会拆掉自己的地基。

## 分歧的根源：消费者可不可控

OKF 是**交换格式**——目标写在 spec（规范）第一节，"跨系统与组织交换知识"。它没法要求对面写得好，所以合规只卡三条，其余全是 `MUST NOT reject`：缺字段不能拒、未知 `type` 不能拒、断链不能拒、缺 `index.md` 不能拒。

这个仓库是**单人单仓库**，消费者只有本人和智能体。所以 `wiki check` 反着来：不合规就非零退出。

下面每一处差异都能追回到这一条。

## type 该放哪

字段不是二选一关系——OKF 同样有 `title` / `tags` / `sources`。真正的差别是类型信息存在哪：

| | 类型信息在哪 | 因此 |
|---|---|---|
| OKF | frontmatter（前置元数据）的 `type` | 目录结构"与领域无关"，怎么组织随生产者 |
| 本仓库 | **路径**（五区 + 固定骨架） | 目录本身携带语义，不需要 `type` |

两个设计**互为前提，不能各取一半**。OKF 必须要 `type`，正因为它的目录不携带语义；本仓库能省掉 `type`，正因为路径已经说清了这页是素材、是认知、还是所知。

要给本仓库补 `type` 就等于承认路径不再可靠——那规则二的固定骨架也就没意义了。

## 三处立场相反

不是本仓库缺功能，是两边故意选了相反的一边。

| | OKF | 本仓库 |
|---|---|---|
| **断链** | 必须容忍，视作"尚未写出的知识" | `check` 当错误，非零退出 |
| **素材** | `references/` 里的镜像件也是一等概念，照样要 `type` 和 frontmatter | 规则三：`raw/` 免 schema，原件就该是原件 |
| **index** | 保留名，无 frontmatter，纯目录清单，可自动生成也可消费时合成 | 文件夹同名页 `X/X.md` 带完整 frontmatter，是**本层正文**，不是清单 |

第三条尤其容易看岔：两边都叫 index，职责完全不同。本仓库把"目录清单"和"本层正文"合并成了一件事——单人仓库里这两件事本来就重合。

## 已经搬过来的：信任层

`generated` / `verified` 和 actor（行为主体）约定直接照搬（[[OKF开放知识格式]] 的信任族一节）。这是全套 spec 里对本仓库最有价值的部分，因为**这个仓库越来越多由智能体写**，而在此之前 frontmatter 分不出"智能体写完没人看过"和"本人确认过"。

搬的时候改了两处：

- **actor（行为主体）去掉版本号**。OKF 写 `<产品>/<版本>`（`reference_agent/gemini-2.5-pro`），这里只写 `claude`。模型版本几个月换一茬，写进 frontmatter 只会变成历史噪音；真要查是哪个版本写的，`git log` 里有。
- **三级信任的名字用中文**（未确认 / 机器确认 / 人工确认），因为它只在 `wiki page unverified` 的输出里出现，不参与交换。

没改的是最要紧的那条设计：**信任层级由 `verified` 推导而不存储**。跟 OKF 处理可信度信号一个思路——只存客观事实，不存会过期的结论。

## 没搬的，以及为什么

| 特性 | 为什么不搬 |
|---|---|
| `sources` 的可信度 signal（信号，含 `author` / `usage_count` / `last_modified`） | 那是给数据平台衡量"这张表还有人用吗"的。个人 wiki 的素材来源就那么几份，信号比噪音还少 |
| `stale_after` | 个人 wiki 没有 SLA。真过期了是读的时候发现，不是定时器发现 |
| Attested Computation（可证明计算） | 给数据平台算指标用的，需要 executor（执行器）和确定性的 attester（见证器）。这里没有要算的数 |
| `log.md` | OKF 要它是因为可能以 tarball（打包文件）分发，那时没有 git。这个仓库只活在 git 里，`git log` 就是 log.md |
| `type` | 见上一节：类型信息已经编码在路径里，补 `type` 等于承认路径不可靠，那规则二的固定骨架也就没意义了。真有交换需求时再说 |

## 生命周期：status

`status`（`draft` / `stable` / `deprecated`，缺省即 `stable`）也照搬了，用 `wiki page mark` 改。

**这里要更正一个早先写在本页的错误判断。** 原来的理由是"`status` 和 `verified` 重叠，'没人确认过'已经表达了'别太当真'"——那是把**实践中都读作"别太当真"**误当成了**语义重叠**。OKF 自己就把两者分在 §5.4（生命周期）和 §5.2（信任）两族，它们回答的是不同问题：

| | 回答什么 | 谁来设 |
|---|---|---|
| `status` | 这页写完了没有、还算不算数 | 写页的人 |
| `verified` | 有没有人核对过内容属实 | 确认的人 |

四种组合都成立：`stable` 但未确认（写完了，没人核过）、`draft` 但人工确认（半成品，但你看过并认可它当前的样子）、`deprecated` 但当年人工确认过（内容那时是对的，现在不该再用）。

真正的风险不在语义，在**用法侵蚀**：一旦有人拿 `status: stable` 表示"已确认"，两个字段就开始互相顶替，而且没有任何机制拦得住。所以规则里写死了一条禁令——**`status` 不表达确认状态，确认状态只看 `verified`**。

搬 `status` 撞掉了一个已有字段：书的阅读进度原先也叫 `status`（`未读` / `在读` / `读完` / `搁置`），改名 `progress` 让位。两者从此各管各的——一本书可以"在读"而它的进度页本身是 `stable`。

`description`（§4.1 的推荐字段）也一并搬了，一句话摘要，供 `wiki list` 和未来的索引用。必填但可留空——建页时留空，因为机器编不出一句诚实的摘要。

## 真要对接 OKF 生态

硬性不合规只有两点：`raw/document/` 下的素材没有 frontmatter（违反合规第一条），全仓库无 `type`（违反第二条）。文件夹页叫 `X/X.md`，不撞 `index.md` 这个保留名，第三条空过。

补齐不难——给每页加 `type`、给素材套上 frontmatter——但代价是废掉规则三，从此 `raw/` 里的东西不再是原件。**在真有交换需求之前不值得**。
