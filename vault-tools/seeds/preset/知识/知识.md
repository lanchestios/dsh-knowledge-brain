## 怎么读

回答「这个概念是什么、这套方法或判据怎么讲」：外部习得、不绑版本的领域知识。

- 按主题目录找概念页，页名就是概念名；先用检索或目录树定位，再读页。
- 概念页有双链指向用到它的 `学习/`、`系统/` 页；问「这个概念在哪个系统里落地」时顺着反链带上一层，不再往下展开。

交回照 `wiki-read` 技能的上下文包：逐字摘原文、出处写到节标题、缺的进「没找到」。

## 骨架按主题类型固定

同类主题用同一副骨架，才能横向比较。

**格式 / 规范类**（OKF、AGENTS.md、各种 spec）

```
定义 → 设计原则 → 结构总览（★ 树 + 全字段表）→ 关键机制 → 合规与版本 → 可信边界
```

`结构总览` 是重心，要一眼看全形状和全部字段（必填性、作用、取值）。

**方法 / 理论类**（信息映射、极简主义、各种方法论）

```
定义 → 出身（谁、何时、解决什么问题）→ 核心构件 → 操作规则 → 可信边界
```

**系统 / 架构类**（Palantir Ontology、各种平台与产品）

```
定义 → 专有名词（★ 按依赖序）→ 概念信息流（★ 图 + 分成哪几部分）→ 来历（可省）→ 与同类的区别（★ 对照表）→ 逐部分拆解 → 构件清单（★ 树 + 全构件表）→ 跨构件机制 → 可信边界
```

规范类写纸面约定，重心在字段；这类写跑着的东西，重心在构件分工与联动。各节要求：

- **专有名词**：按依赖序讲，先讲不依赖别的词的词。检验：通读全页，每个词首次使用都在定义之后。
- **概念信息流**：一张图说清一次请求或一条数据怎么穿过系统，再列分成哪几部分、各一句职责。不出现文件名、目录、行数、代码、完整类型签名。部分按系统自己的职责分，不对齐目录。
- **来历**：谁做的、何时、什么许可。子页一般没有，指回父页，不留空节。
- **与同类的区别**：对照表，列常被对标的东西、各自关心什么、差在哪。放在概念图之后，因为要用到本系统的术语。
- **逐部分拆解**：按上一节的部分一部分一节。统一的结构或过程（包含关系、联合类型、状态机、时序、解析顺序、多对一收敛）一律画图，性质与取舍用文字。
- **构件清单**：树带行数和文件数，信息最密。放在拆解之后，读者先知道系统分几半，清单才挂得上。
- **跨构件机制**：事务、权限、审计、演进等不属于单独某块的运行时性质，集中写一次。

遇到新一类主题，先定骨架再动笔，定完写回本页。
